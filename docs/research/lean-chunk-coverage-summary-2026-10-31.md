**Which relation the statuses describe.** Every status now describes the canonical Gate-B relation,
the successor tier **`allFeatures`** (`Tier.cfg .allFeatures` in `Successor/Config.lean`;
`nearspec-v3-check-successor --tier allFeatures`). Where the signed statement of record
(`D3.checkD3`/`RelD3`, `--tier signed`) or its legacy core (`D3.checkD3Core`) still excludes
something, the row's `domain_guard`/`remaining_work` says so and names the tier. Such an
exclusion is a stated signed-tier restriction, not a Gate-B gap.

**Rules applied** (tool docstring and plan §4 L0):
- `implemented` means a dispatch arm or decided path exists on `allFeatures`.
- `validated` additionally needs whole-chunk fixtures judged by cold pinned nearcore **and** a
  deliberate-breakage control.
- Promotions are derived. The tool first checks the Lean surface: an `allFeatures` flag, a
  `pBaseGlobal` arm, a `cryptoHostCall` arm with a positive and a negative fixture step, a named
  exclusion string. It then applies an evidence entry (`VALIDATION`) whose paths it checks exist.
  If the surface disappears, the row falls back to `partial`/`missing` and `--check` fails.

## L0 row validation (second pass, 2026-10-31)

Evidence package: [l0-row-validation](../evidence/lean-chunk-completion/l0-row-validation/README.md)
(per-row record: `rows.json`, read by `promote_row` in the tool).

**Method.**
1. A control build of the successor checker is generated by `tools/d3/l0_ctl_patch.py` in a copy
   of the tree, never on the default path. It uses `@[implemented_by]` hooks, so no kernel term
   changes.
2. With the trace on, its verdicts and reasons are identical to the freeze checker's on every case:
   - the 51,164-case sample;
   - the 2,218-case supplement;
   - the 132 guard mutants.
3. The trace gives each row's exercising whole-chunk cases. The default replay of those
   populations has 0 verdict disagreements and 0 Lean-accept/nearcore-reject cases. The 16
   comparator "disagreements" are the named `e.code_prep_race` exclusion on pipeline-race fixtures.
4. Each row gets its own control, `NEARSPEC_ABLATE=host:<name>|act:<tag>|guard:<msg>`, replayed on
   up to 16 exercising cases with the repository comparator. The control detects the row when the
   ablated replay has ≥ 1 disagreement and the unablated replay of the same cases passes.
5. For the claim-structure guards, `tools/d3/l0_guard_mutants.py` makes each guard the first
   failure in 12 claim mutants per guard, judged by the claim-v3 discipline.
