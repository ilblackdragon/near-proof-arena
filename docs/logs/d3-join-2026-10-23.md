The previous lane (`pq-prepare-link`) called this lift "a finite case walk, not a research

Evidence classes: **[K]** kernel-checked, **[M]** measured, **[doc]** read/quoted, **[O]** open.

## The target

The join's `.done` arm needs, for the hook's own resolved code blob:

```
functionCall cfg c st ar (.fcall m a g d) = .ok (st', ar') →
ar'.ok = true →
∃ (code : ByteArray) (p : Prepared), prepare cfg code true = .ok p
```

`PrepareLink.runCall_done_prepare_ok` (`[K]`) already gives this at the `runCall` level:
`runCall … = .done s err → ∃ p, prepare … = .ok p`.  What is missing is naming the blob the
hook actually resolved *inside* its `do` block.

## Why the statement is true (the argument is not the problem)

The hook's result can carry `ok = true` from exactly one place.  Enumerated from
`spec/lean/v3/NearSpecV3/D3/FunctionCall.lean:230-361` **[doc]**:

| arm | result | `ok` |
|---|---|---|
| `throw …` (8 sites) | `.error` | n/a — cannot equal `.ok` |
| `Contract.none` | `.ok (st, ar.fail)` | **false** |
| `runCall → .line l` → `lineOutcome` | `.ok (st, {ar.fail with …})` | **false** |
| `runCall → .done s (some e)` (non-unmodeled/non-invalid) | `.ok (st, ar1.fail)` | **false** |
| `runCall → .done s none`, success path | `.ok (st, ar1)` | **`ar.ok`** |

So `ar'.ok = true` forces the last row, i.e. `runCall … = .done s none`, and the lift follows
from `runCall_done_prepare_ok`.  The two `false` rows are definitional:
`AR.fail` sets `ok := false` (`D2/Actions.lean:91-93`), and both `false` rows only change
`gasBurnt`/`gasFC`/`gasUsed`/`logs` around `ar.fail`, so their `.ok` field is `rfl`-equal to
`false` **[K]**:

```lean
example (ar : AR) (x : Nat) : ({ ar.fail with gasBurnt := x }).ok = false := rfl
example (st : ActSt) (ar : AR) (b u : Nat) :
    ({ ar.fail with gasBurnt := ar.gasBurnt + b, gasFC := ar.gasFC + b,
       gasUsed := ar.gasUsed + u } : AR).ok = false := rfl
```

That is the whole mathematical content.  The lift is true.  Getting Lean to *look at* the arm is
the problem.

## Where the peel stops

Reproduced probe (`zk-formal`, `lake env lean`), 2026-10-23.  Using a `peel` macro so the same
three alternatives are tried at every step:

```lean
macro "peel" : tactic =>
  `(tactic| first
      | split at h
      | simp only [Except.bind] at h
      | (exfalso
         simp only [Except.ok.injEq, Prod.mk.injEq] at h
         obtain ⟨-, rfl⟩ := h
         simp only [AR.fail, Bool.false_eq_true] at hok))

simp only [functionCall] at h
repeat' peel
```

`repeat' peel` terminates immediately — **without consuming the first scrutinee** — leaving one
goal whose hypothesis is still headed by

```
h : (match st.account with
      | ⋯ => if AccountId.isEthImplicit c.r.recv = true then … else …
      | ⋯ => ⋯) = ⋯
```

So the first thing the peel has to cross is `match st.account`, and that is precisely where every
automatic mechanism fails:

| attempt at `match st.account` | result |
|---|---|
| `split at h` | does not split it; `peel` falls through to the next alternative and the loop ends |
| `cases hacc : st.account` + `simp only [hacc] at h` | `simp` made no progress — the equation does not rewrite the scrutinee inside `h` |
| `rw [hacc] at h` | pattern not found |
| `by_cases h1 : AccountId.isEthImplicit …` (the *next* scrutinee) | works, but only once the account match is already gone; applied directly it renames the guard under the match and leaves `if false = true` residue |

This is a sharper statement than the earlier lane's.  The blocker is **not** "one leaf, two throws"
at the end of the walk — it is the **first** scrutinee, an `Option` match that came from
do-notation's

```lean
let some acct := st.account | throw "invalid: EXPECT_ACCOUNT_EXISTS"
```

whose desugared matcher in the elaborated term neither `split` nor an equational rewrite will
enter.

### Why the obvious escapes do not work

* **`generalize hrc : runCall _ _ _ _ _ _ _ = rc at h`** produces `hrc : runCall ?m.68 … = rc`
  with *unassigned metavariables* — `generalize`'s pattern must be a closed term and `_` becomes a
  fresh metavar rather than being inferred from the occurrence.  The occurrence is not abstracted,
  so `cases rc` does not split `h`.
* **`cases hacc : st.account with` then `simp only [hacc] at h`** — the rewrite is a no-op on `h`
  ("`simp` made no progress"), and plain `rw [hacc] at h` reports "pattern not found".  The
  desugared `let some acct := …` matcher is not keyed on the projection `st.account` in a way
  these tactics match.
* **Naming the term by hand** requires the full `CallCtx` record literal (~18 fields, containing
  `actionHash`, `sha256`, `env.validators`, …) plus the `TTN.RealStore` literal.  It is writable
  but ~400 lines and would be fragile against any spec edit.
* **`split` has no `discharger` argument** — checked in Lean 4.34.1
  (`Init/Tactics.lean:1205`: `syntax (name := split) "split" (ppSpace colGt term)? (location)?`).
  The `(discharger := …)` syntax exists for `simp`/`dsimp`/`simpa` only.
* **`cases hrc : <term> with`** needs the term too — same problem.

## The path that remains

Two routes, in order of cost.  Both are unstarted; neither is a research problem.

### Route A — destructure the record so the matchers become locals

**This works, and it is the technique the next agent should start from.**  The wall is that every
remaining scrutinee is a *projection* (`st.account`, `acct.contract`).  `split` and `rw` will not
enter a `match` on a projection, and `cases hacc : st.account` does not rewrite `h`.  Destructuring
the structure turns each projection into a plain local, after which `dsimp only at h` reduces the
projection away and `split`/`cases` behave normally:

```lean
simp only [functionCall] at h
obtain ⟨o, account, actor, deploys⟩ := st      -- st becomes a constructor application
dsimp only at h                                 -- `match {…}.account` becomes `match account`
cases account with
| none => …      -- dead: ok = false
| some acct =>
  obtain ⟨accAmt, accLocked, accUsage, contract, accV2⟩ := acct
  dsimp only at h
  by_cases h1 : AccountId.isEthImplicit c.r.recv = true
  · simp only [h1, ite_true] at h
    cases contract with
    | «local» hh => …   -- note: `local` is a keyword, needs «guillemets»
    | none => …
    | global hh => …
    | byAccount id => …
  · simp only [h1, ite_false, Bool.false_eq_true] at h
    cases contract with …
```

Measured effect of each step (probes `A1`–`A11`):

| step | before | after |
|---|---|---|
| `obtain` on `st` | `match st.account` | `match {...}.account` (still blocked) |
| `+ dsimp only at h` | `match st.account` | **`match account`** — a bare local |
| `+ cases account` | blocked | 1 dead goal (`none`, closes) + live `some acct` branch |
| `+ obtain` on `acct` | `match acct.contract` | `match contract` — a bare local |
| `+ cases contract` | blocked | 4 branches, each fully open (`if accAmt + d ≥ 2^128 then …`) |

So three of the four blockers are now crossable and the surviving goals are ordinary
`if`/`do` terms over locals (`accAmt`, `contract`, `o`, …), not projections.

**What still blocks, precisely.**  In the fully-opened branches the remaining peel is
`split at h` over the balance guard, `env.codeOf`, `contractOOD`, and finally the `runCall` match.
Those are the steps earlier probes (`M1`, `M7`) already closed *before* the record destructuring was
introduced, so the expectation is that they close here too — but this session ended before the
combination was driven to completion.  The specific symptom to expect: `cases contract <;> dsimp
only at h <;> simp only [Except.bind] at h` reports "`simp` made no progress" on branches whose
`do` block has already been reduced, so those steps need `try`/`first` guards rather than `<;>`.

Estimate for the next agent: finish that peel (roughly 4–6 more steps per branch, 8 branches
because of the `isEthImplicit` × `contract` product), then the `runCall` split, then the two
`ok = false` closers which are already `rfl` facts.  The search is over; what remains is
mechanical repetition in 8 similar branches.

### Route B — split the obligation at the arm

If Route A stalls on a second matcher, prove the two halves separately:

1. `runCall … = .done s e → ∃ p, prepare … = .ok p` — already **[K]**
   (`PrepareLink.runCall_done_prepare_ok`);
2. `functionCall … = .ok (st', ar') → ar'.ok = true → ∃ s e, runCall … = .done s e` — the arm
   classification, which is the same peel but concludes something weaker, so the `.done`-arm
   bookkeeping (`manager`/`distribute`/`finishActs`) never has to be entered.

Route B is weaker than the unconditional lift but is honest and reusable, and it makes the join's
`.done` premise explicit rather than hidden.

## Correction to the previous lane's estimate

`pq-prepare-link` §"Fourth finding" recorded: *"after `unfold functionCall` plus
`repeat' split at h` the term collapses to a **single** leaf whose hypothesis is the whole nested
`runCall` match, with the two `throw` leaves closing by `simp`."*  Reproduced, that is not what
happens:

* `unfold functionCall` is the worst of the options — it yields **146 goals**, because `unfold`
  inlines the `__do_jp` continuation closures and every `if`/`match` is duplicated per closure.
* `simp only [functionCall] at h` gives a *better* term, but `split` then stops at the **first**
  scrutinee (`match st.account`), not at the last.
* The two `throw` leaves do close, but they are not the blocker and closing them makes no
  difference to the remaining goal.

So the lift is still "mechanical, not done", but the mechanical part is *entering the first
matcher*, not walking the tail.  Recording that saves the next agent the 40-probe search this
session spent.
