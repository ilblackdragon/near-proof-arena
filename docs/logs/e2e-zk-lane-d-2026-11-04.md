## 3. Arity 8

New driver subcommand `tree-arity` (trace generation over a finished run's leaves; optionally
proves one valid node). Over the depth-2 leaves of chunk 2 (`results/zk/d6/arity/`):
* arity 2: program 348,254 rows (= the run's node), NvAir 676,320, SHA 2,322,688 (18,146
  compressions); arity 3: 519,934 / 1,010,688 / 3,482,496 (27,207). Per child: 171,680 program,
  334,368 NvAir, 1,159,808 SHA rows (9,061 compressions); fixed parts ≈ 4.9K / 7.6K / 3K.
* **3-ary node proved** (natural heights, tree layer parameters): 421,407 B, 547 s at 10 threads,
  21.3 GB peak.
* Arity 4 and 8 do not fit. Found: `bind_child_program` requires the node's ALU height to equal
  the child's ("child ALU height must equal ours"; BIND evaluates the node's program on the
  child's domain, and it is emitted for every child, gated in-circuit). So an arity whose NvAir
  exceeds 2^20 needs every tree proof, leaves included, at that NvAir height; the first probe
  run (NvAir 2^23) failed on exactly this. Plus the SHA AIR ceiling: 8-ary = 9.3M SHA rows = 3
  instances at 2^22 (the compression AIR already has `cid_offset`; the generator split, the
  lookback-bus key, the shared table's multiplicities, the AIR order in `shape_pinned_heights` /
  V_d and the tree pin need it).
* 8-ary node estimate: ≈ 1.0G committed cells; 0.8 ks / 29 GB (affine through the 2- and 3-ary
  proofs) to 1.8 ks / 71 GB (linear in cells). Not proved (geometry change + up to 71 GB, above
  the 40 GB cap).
* `scripts/tree_arity_model.py` (CPU view from these numbers; GPU view = `prover-budget/model.py`
  re-anchored on 9,061 compressions per child and 13,429 cells per compression): see README §0.
  Summary: 8-ary saves ≈ 11 % of aggregation work on the GPU model at lb 5 and no latency
  (throughput-bound, 16.3 vs 17.4 s); on this stack's built design (uniform heights) 8-ary is
  worse (leaves padded to 8-ary node size); with leaf heights ≠ node heights and PAD at any level
  it is ≈ 30 % cheaper in work with a longer critical path.
