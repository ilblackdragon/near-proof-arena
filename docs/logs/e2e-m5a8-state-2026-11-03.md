## Findings

* **Completeness, `hplen > ~32,700` B** (sub-agent C): a continued key's own memory
  `50 + 2·hplen` sits in one 16-bit-ish limb of `memChain` (limbs `< 2^17`), so a node key of more
  than ~65,000 nibbles cannot be proved honestly. Not a soundness hole (`memChain_soundW` gives the
  exact equation up to `2^28`). NEAR keys (≤ 2 KiB + prefix, `hplen` ≈ 2,050) are far below.
* **Empty trie key**: `ke` closes the STATE-row gap (no `STB` run for `klen = 0`), but an empty *trie*
  key is not supported elsewhere: the `KEY` table has no row for a 0-byte key (precheck fails on
  `KEY` constraint 14 for a synthetic root-value key), and inserting `[]` into a non-empty trie is
  the "key ends at the new branch" split. NEAR trie keys are never empty (column byte + account);
  an empty *contract* key arrives through the trie-key composition (lane A, M6).
* **Item 4 designs** (not built; each estimated at several sessions of Lean, mostly new `UChain` /
  `DChain` constructors and their ~100 case sites):
  * *split where a key ends at the new branch* (C): `oLX`/`oEX` with `mK` (walk key ends: cases
    `splitLeaf.newEnds`, `splitExt.newEnds`) or `mL` (old leaf ends: `splitLeaf.oldEnds`) instead of
    only `mN`; `oSL` with a value (`nhv = mK + mL`) and exactly one child; value from the walk
    (`dvlen`/`dvh`) or from the old leaf via `SPQ`; `memNew`'s value term generalized to
    `(oUV + oSL·nhv)·vmem`. A continued old key ending at the branch stays blocked by `mL·cont = 0`.
  * *squash onto an extension / branch sibling, squash after a branch-value delete* (S): a result
    kind `RK_XD` (extension descriptor: key `K_kid2[st2 .. e2)`, child ref, child memory) next to
    `RK_LD`; sibling reads `SN.oXS` (extension) and `BR.oBS` (branch memory) on `SIBQ/SIBA`; `BR.oDX`
    + `SN.oXM` to materialize under a branch parent; `SN.oED` generalized to merge an `XD` child.
    Fixture `synth.py squashx` (spec oracle = transcription, `419b6589…2dc9c4`; tracegen stops at
    `Unsupported: squash onto a ext sibling`).
* No soundness hole found in the continued-key AIR (C): several `SNC` rows may claim the same
  `(rid, c)`, but the `KC` chain forces them to the same position and key ids.
