## 2. `PvdAt` and `NodeAsserts` (item 2, `NvProg.lean`)

Chain, all from `NvHold`:

1. `ProgBound tr prog` (premise: program binding, supplied by V_d's opening check at FINAL or the
   parent's anchor/BIND for tree levels): rows `0..|prog|` hold `[A, B + op·2^24, K1, K2]`.
2. `ka_of_p1`: `P1 ≠ 0 ⇒` ALU row (constraint 179).
3. `decode_ok`/`decode_row`: on an ALU row with halves `(a, b)`, constraint 1799 is
   `P1 − (8b + a)·2^24 − rx − 256·ry − 65536·rz` (all 40 cases, partial evaluation of the exported
   expression, `NvAff`).
4. `byte_keys`: ByteAir's 9 exported constraints force its keys to enumerate `(r mod 256, r/256)`
   with last row `(255, 255)` (so height ≤ 2^16) — every key is a byte pair. `byte_class`: every
   NvAir byte-bus count is 0/1 by role (partial evaluation, `byte_counts_role`), except four GLUE-row
   counts (premise `GlueByteBool`). `alu_bytes`: the field LogUp balance of bus 11 forces
   `rx, ry, rz < 256`.
5. `alu_op`: `op = 8b + a` (`40·2^24 < p`). Hence `pvdAt_of` (**`PvdAt` for every `PvD` row of the
   bound program**), `tapeAt_of`, `wrapTape_of_prog` (the D-5 wrap's tape), and
   `asserted_eq`: **every `assert_eq x y` (`Sub x y`; `Zero`) of the bound program gives equal
   cells at `x` and `y`** (Sub/Zero constraints by partial evaluation; memory consistency of the
   three reads, `mem_read`). `contAsserts_of`: `build_agg`'s continuity loop for a read laid out at
   program addresses. `nodeExecV_of_prog`: `NodeExecV` with tape and continuity asserts proved.

Premises left: `ProgBound` (program binding), `GlueByteBool` (GLUE role), the decode-level link
(`NodeLink`: the link half of `NodeAsserts` follows from the asserted cell equalities — a fact
about `build_agg`'s cell layout, not the AIR), `NodeSha`, `NodeInner`.

## Engineering notes

* Kernel evaluation of the exported DAG: expanding `dag j` trees per row hit 34 GB (as in M11f);
  a let-chain evaluator elaborates too slowly. `NvDagEval` evaluates in topological order with a
  block store (~5 s, ~4.5 GB per row). A bounded `decide` over several rows grows superlinearly
  (16 rows did not finish in 40 min): one theorem per row, chained.
* Computing all 792 rows' mem entries in one kernel run needs > 34 GB: the non-zero entries are
  checked per 64-row chunk against `#eval`-generated literals (`NvHonestMemData.lean`), and the
  balance check runs per address bucket on the literal.
* `lake env lean` blocks on the workspace lock while a `lake build` runs; iteration used `lean`
  with the package `LEAN_PATH`.
