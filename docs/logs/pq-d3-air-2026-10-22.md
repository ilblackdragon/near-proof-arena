## 1. The storage hosts, and why the id scheme mattered [K]

`hostFns` was `base ∪ promise ∪ ctx ∪ log/reg ∪ hash`; `storage_read/write/has_key/remove` were
absent, so any contract touching contract storage was out of domain.

`tools/host-fns/canonical.txt` lists storage at 53..59 — **colliding** with the hash block (53..56)
already in `hostFns`. Read literally, `storage_write` (59) would sit inside the hash range and
`storage_has_key` (53) would alias `sha256`. The lane allocates at **57..60**, after the hash block,
so every existing id and every cached `HOSTT` is unchanged.

Four kernel-checked facts (`decide +kernel`, **no axioms**) pin this down:

| theorem | statement |
|---|---|
| `hostFns_ids_nodup` | `(hostFns.map (·.1)).Nodup` — no two entries share an id |
| `hostStorage_sigs` | `hostSig 57/58/59/60 = (3,1)/(5,1)/(2,1)/(3,1)` |
| `hostStorage_names` | each storage name resolves to exactly its id |
| `hostHash_ids_stable` | `hostHashIds = [53,54,55,56]` — cached `HOSTT` rows still resolve |

`hostFns_arity_agrees` and `hostFns_types` (which compare the table against
`NearSpecV3.Wasm.hostSigs`) re-check over the new entries; both `[propext]` only.

`storage_iter_prefix` / `_range` / `_next` are **not** added on purpose: they always
`hErr "Deprecated"` (`Host.lean:795-800`), so they cannot move storage and are out of domain by
construction.

## 2. The test that was missing [M]

Adding table entries left nothing exercising them. Because the HOST chip is *generic* (it carries
`(hid, np, ar)` and passes arguments through `HOSTQ`/`HOSTR`), a missing or wrong entry produces no
bus imbalance — it only shows up as `eligible:false`. That is the same "test passes, meaning is
missing" class as the HOSTB payload bug.

`storkat` (new) round-trips the mock `External` of the spec:

```
storage_write(len=1, ptr=0, vlen=3, vptr=8, reg=0) -> 0   (fresh key)
storage_has_key(len=1, ptr=0)                      -> 1
storage_read(len=1, ptr=0, reg=3)                  -> 1, value in register 3
register_len(3)                                    -> 3
storage_remove(len=1, ptr=0, reg=4)                -> 1
storage_has_key(len=1, ptr=0)                      -> 0
```

result `0*1000 + 1*100 + 3*10 + 0 = 130`.

The independent Python reference now models the four hosts with the spec's `memOrRegH` rule
(`len = 2^64-1` means "read register `ptr`"), so the program is checked three ways like the rest:
Python reference = Lean spec = Rust trace + AIR pre-check.

**Non-vacuity proved by reverting the change**, not asserted:

| tree | result |
|---|---|
| with storage ids | KAT **98/98** |
| `hostFns` restored to the pre-patch list | `FAIL storkat (unexpectedly ineligible)`, **97/98** |
| entries removed *and* theorems kept | kernel `decide` fails at `HostChip.lean:508/516` |

So the KAT catches the regression and the theorems cannot be satisfied without the entries.

Tamper on the storage-call trace: **90/90 rejected**, including `HOST.hid+1` (unbalanced on bus 208
with `hid = 58`, the `storage_write` call), `HOST.np+1`, `HOST.st+1`, and both `HOST.ga0/ga1`.

## 3. Measured consequence, and the one thing it does not buy [M]

With storage present, `d3tiny` with its `if` clamp replaced by `select` — a contract that really
calls `storage_write` — is **`eligible: true`** with `hosts = [48, 6, 49, 58, 45, 50]`.

It does **not** make any unmodified real contract eligible: `kindOf` still has no `.if_`/`.else_`
case. Verified independently — `d3tiny` unmodified is `eligible:false`, and so is a module whose
only import is `storage_iter_prefix` (out of domain by design, as intended).

So link 1 is now two landed, independent pieces:

| piece | state |
|---|---|
| storage hosts | **done** (`ce968bfc3`), KAT + tamper |
| `if`/`else` spec steps | **done** (`55fab1e0f`, lane `pq-if2`): `step_if`, `step_else`, `popN_snd` |
| `if` AIR selector + row lemma | **[O]** — needs its own table (`CTRL` must stay byte-identical; `if` falls through on non-zero, the opposite polarity to `fJif`) |
| `if` checker extension | **[O]** — `analyzeIf`/`verifyAtIf`/`recordAtIf`/`checkModuleIf`, producing exactly `step_if`'s hypotheses |
| `if` tracegen + opcode map | **[O]** |

## 4. Process note, third occurrence [M]

The tracked Rust binary in a fresh worktree is the **pre-REG** build: `run_kat.sh` first reported
**74/97**, the exact signature of the stale-binary trap in the handover. `bin.sh`'s age guard
cannot see it, because the tracked binary's mtime is newer than `src/*.rs` while its *content*
predates them. Rebuilding with `cargo build --release` gives 97/97 (98/98 now).

This is now the fourth distinct instance of one class: the guard covers age, not identity. It
also bit `wasmbase-tool` (the Lean export was stale relative to `HostChip.lean`, so `HOSTB` had 9
columns rather than 10 and tracegen panicked). **Always rebuild both artifacts, and prefer a guard
that checks a content hash over one that checks mtime.**

Second note: the `bin.sh` guard *did* fire correctly when `tracegen.rs` was edited in this lane
(`stale binary: ... tracegen.rs is newer`) — so the guard works for edits it can see; the failure
mode is only the pre-existing tracked binary.
