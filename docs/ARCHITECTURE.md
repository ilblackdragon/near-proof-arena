# Architecture

This document describes NEAR Proof Arena as it is implemented on `main`.
Each statement was checked against the code and cites a file. Where the code
and another document disagree, this document follows the code and says so.
Parts that other lanes are still building are marked **in progress** with
the branch name.

Related documents: `docs/CONTRACTS.md` (frozen interfaces),
`docs/EVIDENCE_COVERAGE.md` (what is checked, trusted, tested or missing),
`docs/TCB.md`, `docs/THREAT_MODEL.md`, `docs/DEPLOYMENT.md`,
`docs/ISOLATION.md`, `docs/FORMAL_INTERFACE.md`, `docs/INTERP_SPEC.md`,
`docs/BENCHMARK_SPEC.md`, `docs/AGENT_CONTRACT.md`.

## 2. Control plane (`server/`)

### 2.1 Listeners and routes

Two listeners (`server/arena-server/src/config.rs`, `src/main.rs`):

* the public and admin API on `ARENA_BIND_ADDR` (default `127.0.0.1:8471`);
* the internal worker API on `ARENA_WORKER_API_BIND_ADDR` (default `127.0.0.1:8472`).

Binding to a non-loopback address requires an `ARENA_HARDENED_CONFIG` TOML
with `allow_non_loopback_bind = true`, and in production also
`behind_tls_proxy = true`.

Public and agent routes (`server/arena-server/src/public.rs`):

| method | path | auth |
|---|---|---|
| GET | `/healthz` | none |
| GET | `/v1/openapi.json` | none |
| GET | `/v1/challenges`, `/v1/challenges/{id}` | none (each read re-verifies id, digest and signature) |
| POST | `/v1/uploads` | agent token; raw body; content-addressed; daily byte quota |
| POST | `/v1/submissions` | agent token; `{challenge_id, upload_digest, idempotency_key, parent?}` |
| GET | `/v1/submissions`, `/v1/submissions/{id}` | none |

### 2.2 Orchestrator state machine

`server/arena-orchestrator/src/lib.rs` (`advance()`), stages from
`common/arena-types/src/pipeline.rs`:

```
 POST /v1/submissions ─► start_run ─► RECEIVED ──VALIDATE──► VALIDATED ──BUILD──► BUILT
                                                                                    │
                                    classify(): NO_PARENT | PROVER_ONLY | VERIFIER_OR_PROTOCOL
                                                                                    │
                    no formal gate required ─────────────────────────────┐          │
                    formal cache hit (reuse_formal) ─────────────────────┤◄─────────┤
                    else enqueue FORMAL_CHECK ──done──────────────────────┤          │
                                                                          ▼
                                                                    FORMAL_CHECKED
                                                     enqueue CONFORMANCE ∥ ADVERSARIAL
                                                                          ▼ both done
                                                                CONFORMANCE_CHECKED
                                                                 enqueue BENCHMARK
                                                                          ▼
                                                                    BENCHMARKED
                                                                          ▼
                                                     DECIDED (finalize: decision, tier,
                                                     score, evidence graph, signed report)

 any mandatory FAIL ──► finalize(FailFast) ──► DECIDED (REJECTED, remaining gates "not run")
 infra failure ──► retry with backoff base·2^(attempt-1), max ARENA_JOB_MAX_ATTEMPTS (3) ──► INFRA_ERROR
 cancel ──► CANCELLED
```

Each transition runs in one transaction that first locks the run row
(`run_for_update`). Job kinds and the gates each one owns
(`server/arena-jobs/src/lib.rs`):

| job kind | gates |
|---|---|
| `VALIDATE` | `PKG_WELLFORMED` |
| `BUILD` | `BUILD_REPRODUCIBLE` |
| `FORMAL_CHECK` | `ARTIFACT_BINDING`, `FORMAL_SEMANTIC_SOUNDNESS`, `FORMAL_SEMANTIC_COMPLETENESS`, `FORMAL_CRYPTO_SOUNDNESS`, `FORMAL_IMPL_CONNECTION`, `FORMAL_ZK`, `AXIOM_AUDIT` |
| `CONFORMANCE` | `CONFORMANCE_DIFFERENTIAL`, `PROVER_RELIABILITY`, `RESOURCE_LIMITS` |
| `ADVERSARIAL` | `ADVERSARIAL_PROOFS` |
| `BENCHMARK` | `BENCHMARK` |

**Decision** (`finalize`, `decide()` in `pipeline.rs`):

* any required/mandatory gate `FAIL` gives `REJECTED`; `NOT_APPLICABLE` also
  rejects unless the gate is in the challenge's `not_applicable_gates`;
* otherwise any missing or `UNKNOWN` gate gives `INCONCLUSIVE`;
* otherwise `ADMITTED`, `accepted = true`;
* `OBLIGATION_UNDISCHARGED` is added when required gates never ran, and
  `DEMO_ONLY` when the effective tier is below the challenge tier;
* defense in depth: on a `formal` challenge, an `ADMITTED` run whose effective
  tier is below `formal` becomes `INCONCLUSIVE`.

**Tiers.** Ranks are demo=0, experimental=1, formal=2
(`server/arena-db/src/lib.rs`). Effective tier = min(challenge tier, every job
result's `tier_cap`). A result's cap = min(job tier, the worker's registered
cap, the cap the result claims), and it is forced to demo when the sandbox
backend is `bwrap-dev` (`server/arena-orchestrator/src/normalize.rs`).
Lowering is audited as `run.tier_capped`. Leasing offers a job only to a
worker whose `tier_cap` is at least the job's tier. The DB also enforces
`bwrap-dev ⇒ tier_cap = 0` with a CHECK constraint on `workers`.

**Score.** The server recomputes the score and ignores any score a worker
reports (`server/arena-orchestrator/src/score.rs`):
`100 · exp(Σ w_j · ln(baseline_j / median_j))`, in milli-units. The result is
`None` if any baseline is missing. Neither signed challenge has a baseline yet
(`"baseline_ns": []`), so no run can currently receive a score.

**Leaderboard** (`server/arena-db/src/views.rs`, `compute_leaderboard`). A
submission is ranked only if the challenge tier, the run's challenge tier and
its effective tier are all `formal`, the decision is `ADMITTED` and accepted,
it has a score, and it is not revoked. Everything else is listed unranked.

### 2.3 Change classification and formal cache

* **Verified surface** (`VerifiedSurface`, `common/arena-types/src/pipeline.rs`):
  challenge id, verify and prepare artifacts, public-artifacts tree, formal
  tree, certificate declaration, checker image.
* **Classification** (`classify`, `server/arena-orchestrator/src/lib.rs`) runs
  after a passing BUILD. With no parent the class is `NO_PARENT`. Otherwise
  the surface is compared with the parent's latest run that has one: equal
  gives `PROVER_ONLY`, different gives `VERIFIER_OR_PROTOCOL`. The class is
  recorded and audited (`run.change_class`) but **does not affect control
  flow**. Cache reuse is decided by the cache key alone.
* **Cache key** (`server/arena-orchestrator/src/cache.rs`): sha256 of JCS of
  `{v: "arena-formal-cache-v1", challenge_digest, verified_surface,
  checker_image, sorted assumptions, axiom_allowlist, recheckers,
  lean_toolchain}`. Because the challenge digest is part of the key, results
  never carry across challenges, including superseded ones.
* **Reuse** (`reuse_formal`): at BUILT, a live entry whose tier is at least
  the challenge tier is copied into `gate_results` (with `mandatory`
  recomputed and `reused_from` set) and its evidence graph is merged. Audited
  as `formal.cache_reused`.
* **Store**: written only for a "definite" FORMAL_CHECK result, meaning every
  owned gate was reported and none is `UNKNOWN` (`normalize.rs`).
* **Invalidate**: `POST /v1/admin/formal-cache/invalidate` by `checker_image`
  and/or assumption id. Entries are never deleted.

The reference backends demonstrate the intended use.
`examples/reexec-witness-fast` differs from `examples/reexec-witness` only in
prover source (`src/engine.rs`, `src/trie.rs`); their `formal/` trees are
byte-identical, so the fast child is a `PROVER_ONLY` change.

### 2.4 Evidence graph

Types: `common/arena-types/src/evidence.rs`. Node kinds are
`nearcore_source`, `formal_semantics`, `backend_semantics`, `theorem`,
`assumption`, `artifact`, `tcb_component`, `test_suite` and `measurement`.
Edge status is one of `checked`, `trusted`, `tested` or `missing`.

Construction:

1. Each job result may carry an `evidence_graph`. The server sanitizes it to
   at most 2000 nodes and 2000 edges, then merges it into
   `runs.evidence_graph` (`merge_graphs`, `normalize.rs`). Nodes are keyed by
   id and edges by `(from, to, kind)`. **The last write wins.** This happens
   on every completion and on a cache hit.
2. The server never creates nodes itself.
3. The only real producer is `runners/formal-checker/src/report.rs`
   (`evidence_graph()`). Its nodes are `formal:certificate`,
   `formal:expected_statement`, `tcb:lean_toolchain`, `formal:trusted:*`,
   `formal:axiom:*`, `tcb:<rechecker>`, `formal:verifier_model`,
   `artifact:verifier_binary` and `tcb:lean_compiler_runtime`. Its edges are
   `proves`, `defined_in`, `assumes`, `rechecked_by`,
   `contains_candidate_model`, `proves_obligations_about`, `built_from` and
   `implements`. The `implements` edge is always `trusted` for native-lean.
4. `runners/worker` emits no graph. Its `JobOutput` has no such field.
5. Nothing emits `nearcore_source`, `test_suite` or `measurement` nodes. The
   nearcore → spec edge (§8) therefore never appears in a report, although
   `CONTRACTS.md` §8 requires it to be "rendered, never hidden". The web
   renders whatever graph exists (`web/src/components/EvidenceGraphView.tsx`).

Open design point: because the merge is last-write-wins, a later result can
overwrite an earlier `missing` edge with a stronger status. Making the merge
keep the weaker status would make it monotone.

### 2.5 Signed reports

* The key is ed25519 and only the control plane holds it. It is loaded from
  `ARENA_REPORT_SIGNING_KEY_FILE` (PKCS#8 PEM or a 64-hex seed; the file must
  not be group- or other-accessible). Inline `ARENA_REPORT_SIGNING_KEY` works
  in dev only, and dev falls back to an ephemeral key
  (`server/arena-server/src/config.rs`).
* The signature covers the JCS bytes of an `arena-report-v1` document: judge
  version and public key; the challenge (id, digest, tier, governance key,
  scope, excludes, profile, obligations); the submission and run (decision,
  tiers, score, change class, reason codes, not-run gates); the manifest,
  verified surface and build outputs; the formal cache key and `reused_from`;
  gates, jobs, public artifacts, benchmark, evidence graph and disclaimers
  (`server/arena-orchestrator/src/report.rs`).
* Signed at decision time and stored in the `reports` table.
* `GET .../report` returns `{algorithm, canonicalization, public_key,
  signature, report, revocation}`. The `revocation` field is **outside** the
  signature.

## 3. Storage

### 3.1 PostgreSQL

One migration, `server/arena-db/migrations/0001_init.sql`:

| table | purpose | mutability |
|---|---|---|
| `agents`, `admins`, `workers` | principals (token sha256); `workers.sandbox_backend`, `tier_cap` (CHECK: bwrap-dev ⇒ 0) | updatable |
| `challenges` | signed definitions (JCS bytes, signature, governance key) | trigger: only `open` may change; no delete |
| `uploads` | agent package uploads, unique per (agent, digest) | insert |
| `artifacts` | objects uploaded by workers | insert |
| `submissions` | immutable submissions; idempotency per agent; `parent_id` | immutable (trigger) |
| `runs` | one evaluation: stage, decision, tiers, change_class, verified_surface, formal_cache_key, benchmark, evidence_graph | immutable once decided (trigger) |
| `gate_results` | one per (run, gate) | immutable |
| `jobs` | durable queue; queued/leased/done/failed/cancelled; unique per (run, kind) | updatable |
| `audit_events` | append-only log; feeds SSE | triggers block UPDATE/DELETE/TRUNCATE |
| `revocations` | one per submission | immutable |
| `formal_cache` | content-addressed formal results | never deleted; invalidated at most once |
| `quotas` | per-agent overrides | updatable |
| `reports` | signed report bytes | immutable |

Roles:

* **Split roles** (`server/arena-db/src/roles.rs`, `arena-server roles-sql`):
  `arena_api`, `arena_worker` (the worker-gateway pool *inside the server*)
  and `arena_admin`. No role is ever granted DELETE or TRUNCATE; this is
  tested in `roles.rs`.
* **Reference deployment** (`deploy/sql/roles.sql`, plus
  `deploy/sql/grants.sql` generated by `arena-server grants-sql` and kept in
  sync by a test):
  * `arena_owner` runs migrations only.
  * `arena_api` holds the union of the server's needs.
  * `arena_worker` has **no table access**.
  * `arena_backup` has `pg_read_all_data`.
  * `arena_readonly` can read everything except the principal tables.

### 3.2 Object store

`server/arena-store/src/lib.rs` provides `FsStore` behind the `ObjectStore`
trait. Files are laid out as `<root>/objects/<hex[0..2]>/<hex>`, keyed by
the sha256 of the raw bytes. Writes are staged in `tmp/` and hashed and
size-bounded as they are written, then fsynced and atomically renamed. Reads
re-hash the content. **Only a filesystem backend exists**; there is no S3
backend.

## 4. Workers and sandboxes (`runners/`)

### 4.1 `arena-worker`

* **CLI** (`runners/worker/src/main.rs`):
  * `arena-worker` runs the daemon;
  * `arena-worker once`;
  * `arena-worker run-job JOB.json --store DIR` (always bwrap-dev);
  * `__arena-sandbox-helper` is an internal entry point.
* **Configuration** (`runners/worker/src/config.rs`):
  * `ARENA_SERVER_URL`;
  * `ARENA_WORKER_TOKEN` or `ARENA_WORKER_TOKEN_FILE`;
  * `ARENA_WORKER_ID`;
  * `ARENA_SANDBOX_BACKEND` (`bwrap-dev` by default, or `firecracker`);
  * `ARENA_WORKER_KINDS`;
  * `ARENA_WORK_DIR`, `ARENA_IMAGES_DIR`, `ARENA_BENCH_CPUS`, `ARENA_BUILD_*`.
* **No database credentials.** The worker refuses to start if `DATABASE_URL`,
  `PG*` or any `ARENA_*` key containing `database` is set, or if any value
  looks like a Postgres URL.

Stages (`runners/worker/src/stages/`):

| stage | gates | what runs |
|---|---|---|
| `validate` | `PKG_WELLFORMED` | archive and manifest checks via `runners/archive`; no candidate code |
| `build` | `BUILD_REPRODUCIBLE` | `build.sh` twice, offline, `SOURCE_DATE_EPOCH`; outputs must be bit-identical |
| `conformance` | `CONFORMANCE_DIFFERENTIAL`, `PROVER_RELIABILITY`, `RESOURCE_LIMITS` | judge-run `prepare` (public dir frozen by digest); per case `prove` with the witness, claim must equal the oracle's expected claim (`CLAIM_MISMATCH`); `verify` in a separate sandbox without the witness |
| `adversarial` | `ADVERSARIAL_PROOFS` | mutated proofs: built-in `truncate`/`bitflip`/`empty`/`oversize`/`swap`/`append` and 15 mutators from `adversarial/proof-mutators`; determinism check (`VERIFIER_NONDETERMINISTIC`) |
| `benchmark` | `BENCHMARK`, `RESOURCE_LIMITS`, `PROVER_RELIABILITY` | `runners/measure::run_session`: seeded schedule, median/MAD, caching tripwire, VMM-wall cross-check |

Verification in every stage runs the candidate's `entry.verify`
(`runners/worker/src/stages/common.rs`, `run_verify`). The worker has no
`npai-v1` or `native-lean` execution path yet (see §9).

### 4.2 Sandboxes

The trait is `Sandbox { name, tier_cap, layout, run }`
(`runners/sandbox/src/spec.rs`).

**`bwrap-dev`** (`runners/sandbox/src/bwrap.rs`) is for demos only.

* What it does:
  * namespaces: `--unshare-all`, `--disable-userns`, `--clearenv`;
  * a read-only `/usr`, a sized tmpfs at `/scratch`, read-only inputs and a
    read-only `/`;
  * the helper runs as PID 1;
  * resource limits through a delegated cgroup v2 (`systemd-run --user`), or
    an rlimit fallback.
* Why it is demo-only: it shares the host kernel and installs **no seccomp
  filter**.
* How the demo cap is enforced:
  * `BwrapDev::new` and `run` refuse to work without `ARENA_DEV_UNSAFE=1`;
  * `tier_cap()` returns `Demo`, and outcomes are stamped
    `bwrap-dev (DEMO-only)`;
  * the worker adds `DEMO_ONLY` to every gate (`runners/worker/src/executor.rs`);
  * the server enforces the cap again (§2.2).

**`firecracker`** (`runners/firecracker`) is the production backend. It is
fully implemented and is not a stub. Its layers:

1. the unprivileged host library;
2. a delivery container (`--network none`, minimal capabilities, read-only
   rootfs, `arena-fc-shim` as PID 1);
3. the jailer and Firecracker (`--no-api`, default seccomp);
4. the microVM, which is the security boundary;
5. the guest `arena-init`, which runs the candidate as uid 1000 in a cgroup
   and chroot with `NO_NEW_PRIVS`.

There is **no network and no vsock**. I/O uses raw virtio-blk drives: rootfs
`vda`, control `vdb` (`ARENACTL`), output `vdc` (`ARENAOUT`), scratch `vdd`
and mounts from `vde`. Serial markers `ARENA-START`/`ARENA-EXIT` give
host-side timing (`runners/firecracker/proto/src/lib.rs`, `PROTO_VERSION=2`).

Its tests (`runners/firecracker/tests/vm.rs`, 19 tests; `tests/lean_checker.rs`)
are gated on `ARENA_FC_TESTS=1` and the prebuilt images
(`deploy/images/{firecracker,rootfs,fc-runner}`), so they **do not run in
CI**. See `docs/ISOLATION.md`.

## 5. Formal checking

### 5.1 What a certificate must prove

`formal-core/ArenaCore/Admission.lean` defines `AdmissionStatement ch art`:

```
∃ pub v, sha256 pub = art.publicDigest
       ∧ art.impl.Connection ch.verifyFuel v
       ∧ ∃ bk, Obligations ch pub v bk
Obligations = { semSound, semComplete, verifierComplete, cryptoSound }
CryptoSound = DeterministicSound
            ∨ (sha256_cr allowed ∧ CRReduction within maxReductionFuel ∧ CRSecure)
            ∨ (sha256_rom allowed ∧ prover complete ∧ num·2^targetBits ≤ den ∧ RomSound)
VerifierImpl = .interp digest                          -- npai-v1: connection checked
             | .nativeTrusted binDigest toolchainId m  -- native-lean: Connection is v = m (trusted)
```

The relation is `NearSpec`'s `NearRelation` with `WfClaim` (`spec/lean`). The
judge renders the expected statement from the challenge (relation,
profile, `formal_params`: `verify_fuel = 2^30`, `max_proof_bytes = 8 MiB`,
`max_reduction_fuel = 2^30`) and compares it with the certificate's type.

### 5.2 Checker stages (`runners/formal-checker/src/pipeline.rs`)

```
 candidate formal/  ──► staging (only .lean files; candidate lakefile parsed, never run;
                         reserved names / import resolution checked)
   Stage A  untrusted elaboration: `lean -o` per module, offline, in a sandbox,
            against read-only trusted .olean (ArenaCore, NearSpec, judge-generated Expected)
   Stage B  clean recheck in fresh sandboxes:
            B1 leanchecker (Lean kernel replay)      B2 lean4export → NDJSON
            B3 nanoda (independent Rust kernel)       B4 lean4lean (if installed)
            default required: leanchecker + nanoda
   Stage C  judge checks: arena-audit (Lean, environment API: certificate type == expected
            type, no implemented_by/extern/init/unsafe) and a Rust NDJSON audit
            (shadowing, structural equality, transitive axioms); both must agree
            axioms: sorryAx → SORRY_FOUND; ofReduceBool/ofReduceNat/trustCompiler → NATIVE_EVAL_FOUND;
                    unapproved trusted-module axiom → UNAPPROVED_ASSUMPTION; other → FORBIDDEN_AXIOM
            allowlist default: propext, Quot.sound, Classical.choice
```

Tool pins: `runners/formal-checker/tools.toml` (lean4export, nanoda,
lean4lean) and `lean-toolchain` = `leanprover/lean4:v4.34.1`.

The four `FORMAL_*` gates are not checked separately. All of them pass or
fail together, with `AXIOM_AUDIT`, on "certificate type = expected
`AdmissionStatement`, and the rechecks accept" (`runners/formal-checker/src/report.rs`).
The only distinction between them is how findings are scoped per conjunct.
`FORMAL_ZK` has no Lean definition in `formal-core`; it exists only as an
obligation id and as a policy rule.

### 5.3 Verifier routes

`common/arena-types/src/candidate.rs` `VerifyRoute`: `"native"` (default),
`"npai-v1"` and `"native-lean"`. Inside the checker these map to
`native::VerifierRoute { Standard, NativeLean, CandidateNative }`.

* **`npai-v1`**: the statement is about `.interp digest`, where the digest is
  the sha256 of the candidate's `verifier.npai` image, spliced into the
  template (`runners/formal-checker/src/challenge.rs`). The kernel checks the
  certificate against `ArenaCore.Interp.interpVerify` on exactly those bytes.
  The remaining link, the Rust `npai-verify` computing `interpVerify`, is
  differential-tested (§5.4).
* **`native-lean`**: the judge compiles `formal.verifier_model` itself
  (`lean -c`, `leanc -c -O3`, link; `pipeline.rs`, `native.rs`), adds an
  `ARTIFACT_BINDING` gate, and never admits the candidate's own `verify`. The
  Lean compiler and runtime are trusted, and the graph edge is `implements:
  trusted`.
* **`native`**: a candidate-built native verifier (`CandidateNative`). It is
  never admitted on a formal challenge.

### 5.4 NPAI interpreter (`runners/npai`)

* `src/interp.rs` (`#![forbid(unsafe_code)]`) transcribes
  `formal-core/ArenaCore/Interp.lean`; the specification is restated in
  `docs/INTERP_SPEC.md`.
* Instructions: `halt`, `const`, `mov`, ALU ops, `addi`, `jmp`/`jz`/`jnz`,
  tape ops, `ld8`/`st8`, `sha256`, `memeq`, `rohash`, `out`.
* Binaries:
  * `npai-verify`, which is in the TCB. Exit codes: 0 accept, 1 reject,
    2 usage, 3 digest mismatch.
  * `npai-asm`.
  * `npai-difftest`, which compares against the Lean reference executable
    `arena-interp-ref` (`formal-core/InterpRef.lean`).
  * `npai-bench`.
* Fuzz targets: `fuzz/fuzz_targets/{decode,exec}`.
* Tests: `tests/vectors.rs`, which checks the 45 vectors in
  `formal-core/vectors/npai-v1.json` byte for byte, and `tests/asm.rs`.
* `runners/npai/README.md` reports difftest runs of 200,001 and 1,000,000
  cases with 0 disagreements. No report artifact is committed.
* `examples/npai-ir` proves a structured-IR → NPAI compiler correct
  (`NpaiIR.exec_placed`). The NEAR verifier on this route is **not** done:
  the missing theorem is `interpVerify code … ↔ check`.
  **In progress: `lane/npai-near`.**

## 6. NEAR semantics, oracle and claims

* **`spec/lean` (`NearSpec`)**. `TransferV1.applyReceipt` models
  single-Transfer action receipts on protocol version 86, mainnet:
  * account lookup in a partial trie;
  * checked add, and the storage-stake check;
  * burn price `min(receipt price, block price)`;
  * a constant `G` for gas;
  * the gas-price-surplus refund receipt;
  * outcomes and their roots.

  Everything else (failures, rollback, deposit refunds, other actions) is out
  of domain and returns `none`. The challenge's
  `semantic_scope.excludes` lists 23 excluded properties. The post-state root
  is a slice projection (`slicePostRoot`), **not** the on-chain root.
* **Claim encoding**. `spec/claim-v1.md` defines the bytes of `request.bin`,
  `witness.bin`, `claim.bin` and `params.bin`. Codec round-trip and
  injectivity are proved in `NearSpec.ClaimCodec`.
* **Oracle** (`oracle/`, binary `near-arena-oracle`: `gen`, `replay`, `params`).
  It links the pinned nearcore crates by path through `vendor/nearcore`
  (`oracle/scripts/link-nearcore.sh` checks HEAD against `oracle/NEARCORE_PIN`:
  tag 2.13.4, commit `44f7ae6c…`, protocol 86), runs `Runtime::apply`, and
  cross-checks with `Trie::from_recorded_storage`. It is not a member of the
  workspace and not built in CI.
* **Fixtures**. `oracle/fixtures/public/cases` holds 20 cases and
  `oracle/fixtures/rejection/cases` holds 14. All use synthetic state.
* **Three-way difftest** (`spec/difftest-report.json`, seed 4242). It
  compares the nearcore oracle, the Lean `nearspec-check` and the Python
  `oracle/tools/spec_check.py` on **1712 cases**: 1502 in domain, 210 out of
  domain, **0 disagreements**.
* **Workloads**: `spec/workloads/near-transfer-receipt-v1/batch-{1,16,256}.json`.
* **Held-out set**: only a commitment is in the repo
  (`spec/challenge-inputs/heldout-commitment.json`); the seed is kept off-repo.

**Wiring gap.** The server's `ConformanceJob` is an `ExecJob`
`{ctx, challenge, manifest, build}` (`server/arena-jobs/src/lib.rs`) and
carries no oracle cases. The worker's `ConformanceJob` expects `cases[]` with
request, witness and expected-claim digests (`runners/worker/src/jobs.rs`).
Nothing in the server loads oracle fixtures or held-out cases into jobs yet.

## 7. Challenges and governance

```
 drafts/*.draft.json ──arena-admin check──► policy OK
        │                                       │
        └──────────arena-admin sign --key ──────┴──► challenges/chl_<32hex>.json (pretty, normal form)
                                                     challenges/chl_<32hex>.sig  (ed25519 over JCS, hex)
 arena-server startup: ARENA_CHALLENGES_DIR ─► verify sig + id + Governance::check ─► challenges table
 or POST /v1/admin/challenges {definition, signature}
 every read: re-verify bytes, id/digest, signature (server/arena-db/src/challenge.rs)
 upgrade: tools/upgrade-monitor ─► report ─► arena-admin supersede --old --draft ─► new chl_<id>
```

* **Id.** The challenge id is `chl_` followed by the first 32 hex characters
  of `sha256(JCS(definition))` (`common/arena-types/src/challenge.rs`).
* **Policy** (`tools/arena-admin/src/policy.rs`):
  * governed profiles and assumptions;
  * axiom allowlist ⊆ {propext, Classical.choice, Quot.sound};
  * obligations required per tier;
  * weights must sum to 10^6 ppm;
  * a `formal` challenge needs at least one rechecker and `measured_runs` ≥ 5;
  * the all-zero digest is allowed only on `demo`.

  `arena-admin sign` refuses to sign a `formal` challenge with a `dev_only`
  key. On the server, `Governance::check` (`server/arena-orchestrator/src/lib.rs`)
  runs the full policy only when `ARENA_SECURITY_DIR` is set; otherwise it
  only rejects formal-with-dev-key.
* **Keys** (`tools/arena-admin/src/keys.rs`). The key id is `gov_` followed by
  16 hex characters of `sha256(pubkey)`. Public key files use
  `arena-governance-pubkey-v1`. Private key files are refused when inside a
  git tree or group/other-readable. The committed public keys are
  `challenges/governance-dev.pub` (`gov_8292e8f55c257fcc`, `dev_only`) and
  `challenges/governance-local.pub` (`gov_7e075bd83a3313b5`, local operator).
  No production key exists.
* **Signed challenges:**
  * `chl_54c65fe7c73c5abcfe500681889177bc`, `demo-toy-arithmetic`, tier demo,
    dev key;
  * `chl_5ef2bc7d2068219635426e47ca46bfbb`, `near-transfer-receipt-v1`, tier
    formal, local key; requires all 13 obligations except `FORMAL_ZK`.
* **Supersession** happens offline only. `arena-admin supersede` requires
  `supersedes == old id`, a strictly later `created_at`, and no
  protocol-version downgrade. **The server ignores `supersedes`**: it neither
  closes nor links the old challenge. Admins can only toggle `open`. See
  `docs/PROTOCOL_UPGRADES.md`.
* **Next challenge version: in progress on `lane/challenge-v2` and
  `lane/spec-v2`.**

## 9. Known integration gaps

These are verified against the code. Their fixes belong to the integration
e2e lane, which is **in progress**.

1. **Protocol mismatch between the worker and the server.**
   * `runners/worker/src/client.rs` posts to `/internal/v1/jobs/{heartbeat,complete,fail}`
     with `{job_id, worker_id, attempt}` and no `lease_id`.
   * The server expects `/internal/v1/jobs/{id}/…` with `lease_id`.
   * The worker sends job kinds in lowercase; the server uses
     SCREAMING_SNAKE_CASE.
   * `runners/worker/src/jobs.rs` has its own `JobSpec`/`JobOutput`, which
     lack build outputs and an evidence graph. The file's header says the two
     crates are "to be reconciled by the integrator".
2. **No worker runs `FORMAL_CHECK`.** The worker's `JobKind` has five
   variants and none of them is formal. `runners/formal-checker` is a
   standalone CLI (`formal-check`) and library.
3. **No worker runs `npai-v1` or the judge-built `native-lean` verifier.**
   The stages always execute `entry.verify`.
4. **Conformance jobs carry no oracle cases** (§6).
5. **Dev and deploy configuration does not match the worker binary.**
   * `deploy/local/gen-dev-secrets.sh` writes `ARENA_WORKER_DATABASE_URL`
     into `worker.env`, so `make dev-worker` exits with "refusing to start:
     database credentials visible to the worker". This was reproduced.
   * Compose and the Makefile set `ARENA_SANDBOX` and `ARENA_WORKER_CLASSES`,
     but the binary reads `ARENA_SANDBOX_BACKEND` and `ARENA_WORKER_KINDS`.
   * `deploy/hardened/systemd/arena-worker@.service` passes `--class %i`,
     which the binary rejects.
6. **No evidence-graph producer for the nearcore, test-suite and measurement
   edges** (§2.4).
7. **No baselines** in the signed challenges, so no score and no ranked entry
   are possible (§2.2).
8. **The server ignores `supersedes`** (§7).

## 10. Trust boundaries and credentials

```
 ┌────────────────────── untrusted ───────────────────────┐
 │ agents, candidate packages (source, Lean, build.sh,     │
 │ binaries, stdout), web visitors                          │
 └──────────────┬──────────────────────────────────────────┘
                │ agent token (Bearer; sha256 in `agents`)
 ┌──────────────▼──── control plane host ──────────────────┐
 │ arena-server: DB URL (arena_api), report signing key,    │
 │ object store, token hashes, governance PUBLIC keys       │
 └──────────────┬───────────────────────────▲──────────────┘
                │ arena_api (5432)          │ worker token, 8472 only
 ┌──────────────▼───────┐        ┌──────────┴───────────────────────────┐
 │ PostgreSQL           │        │ worker host: worker token only;       │
 │ (owner role: migrate)│        │ no DB creds, no report key, no admin  │
 └──────────────────────┘        │ token (arena-guard worker refuses)    │
                                 │   └─ sandbox (microVM): candidate code│
                                 │      no network, no credentials       │
                                 └───────────────────────────────────────┘
 offline: governance PRIVATE keys (arena-admin; refused inside a git tree / group-readable)
```

| credential | held by | stored as | enforced in |
|---|---|---|---|
| DB URL `arena_api` | arena-server only | env / secret file | worker refuses any DB URL (`runners/worker/src/config.rs`); `grants.sql` gives `arena_worker` nothing |
| DB URL `arena_owner` | `arena-server migrate` / `arena-migrate.service` | `ARENA_MIGRATE_DATABASE_URL` | separate unit |
| report signing key (ed25519) | arena-server only | `ARENA_REPORT_SIGNING_KEY_FILE` (0600) | `arena-guard worker` refuses its presence; inline key refused in production |
| worker token | each worker | `ARENA_WORKER_TOKEN[_FILE]`; server keeps sha256 | worker API only on 8472; `workers.tier_cap` bounds what it can certify |
| agent token | agents | `ARENA_TOKEN`; server keeps sha256 | rate limit and quotas (`server/arena-server/src/ratelimit.rs`) |
| admin token | operators | server keeps sha256; `ARENA_ADMIN_TOKEN[_SHA256]` bootstrap | separate admin pool; refused on workers by the guard |
| governance private key | offline governance | JSON seed file, 0600, outside git | `tools/arena-admin/src/keys.rs`; server holds only public keys (`ARENA_GOVERNANCE_PUBKEY[S|_FILE]`) |

Production refuses `ARENA_DEV_UNSAFE`, `ARENA_SECRETS_ORIGIN=dev-generator`,
inline signing keys and dev-only governance keys
(`server/arena-server/src/config.rs`, `deploy/scripts/arena-guard`).

What a compromised component can do is covered in `docs/THREAT_MODEL.md`. In
short: a worker is trusted to execute gates honestly (TCB #15), and
per-worker signed gate results are aspirational.

## 11. Web and SDK

  `/challenges/:id`, `/submissions`, `/submissions/:id` and `/compare`. It
  makes only GET calls to `/v1/*` (`web/src/api/client.ts`), with

  `submit`, `status`, `report`, `cancel`, `leaderboard`, `challenge`,
  `challenges`. `check-local` reuses `runners/archive` and runs a local
  emulation whose result is marked `"official": false`.

  (`sdk/typescript`, `@near-arena/client`) clients have generated types
  checked against `common/schemas`.
* The template is `sdk/templates/empty`. The worked examples are in
  `examples/`.
