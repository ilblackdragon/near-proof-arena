# Whole-chunk curve-host fixtures (W05)

Pinned nearcore `44f7ae6cd7ef08bab604e20a473bf77e35d4c993`, PV86. Generated by the separate
`oracle/v3-successor` crate with `NEAR_SUCCESSOR_SCENARIO=curve-hosts`; no signed oracle source was
changed and `spec/tools/check_oracle_pins.py` passes.

A contract (`oracle/v3-successor/contracts/curvehosts.wat`) with one method per host and input source
is deployed on `s0curvehosts` and `s2curvehosts`. 149 deterministic FunctionCalls
(`steps.json`, built by `src/curve_hosts.rs`) call every alt_bn128 and BLS12-381 host, plus
`p256_verify` and `ecrecover`. Each call returns the host's u64 result followed by register 1 with
`value_return`, and writes the same bytes to storage key `o`. Host outputs therefore reach the
outcome root and the state root. Inputs are built with the crates nearcore links (zeropool-bn, blst,
p256 at nearcore's lock versions, and near-crypto's secp256k1). Every output, error message and gas
figure here is the validator's own. A label names the input class, not an expected result:

- `pos`: a well-formed valid input.
- `neg`: a malformed or invalid input, whether nearcore answers with a host error or a failure code.
- `edge`: a corner case. These are non-subgroup points in sums and decompression, scalars ≥ r, the
  `(0, ±2)` point, and empty or over-long p256 prehashes.

"chunks" counts the distinct honest chunks that executed that host's steps. One chunk can execute
several steps, since up to three are submitted per height. Per-step detail is in
`manifest-4242.json` under `steps`. It records the label, receipt, chunk, nearcore status, the exact
returned bytes' hash and length, gas burnt and the nonzero ext-cost profile.

The negative inputs include the following:

- Lengths that are not a multiple of the item size (an error for every host).
- Non-canonical `Fq`/`Fp`/`Fp2` coordinates: the coordinate equals p, or x + p.
- alt_bn128 scalars equal to r or 2²⁵⁶−1. These are errors; BLS accepts any 256-bit scalar.
- Off-curve points.
- Non-subgroup points: an alt_bn128 twist point; BLS G1 and G2 points in multiexp and pairing.
- Sign bytes other than 0/1.
- Compression, infinity and sort flag misuse.
- The `(0, ±2)` point, which is rejected because `bls12381_not_in_group_fix = false` at PV86.
- Register input (`value_len = u64::MAX`). For `p1_sum`, the per-element charge divides
  `u64::MAX` by the item size and hits IntegerOverflow. alt_bn128 and BLS pairing count elements
  from the data that was read, so register input succeeds there.
- Out-of-bounds memory.
- Gas exhaustion at the per-element charge.
- For p256: r = 0, s = n, a 0x04 prefix, an x-coordinate off the curve, wrong lengths, and an
  empty prehash.
- For ecrecover: v = 4, flag = 2, wrong lengths, and r = 0.

Observed PV86 behaviour worth noting:

- Non-subgroup points are accepted by `p1_sum`, `p2_sum`, `p1_decompress` and `p2_decompress`
  (return 0). They are rejected by multiexp and pairing (return 1).
- An empty BLS pairing input returns 0.
- High-s p256 signatures verify.
- An empty p256 prehash returns 0. A 64-byte prehash verifies against the signature of its first
  32 bytes.

A second, independent run (seed 31337, chain index 1: 5 shards, 100 seats, zero gas price) executed
the same 149 steps over 94 chunks. Every step's nearcore outcome class and returned bytes are
identical across the two runs. Gas burnt differs on 39 steps through storage and trie-shape costs.

## Lean results

Checker: `nearspec-v3-check-successor --tier allFeatures` built from this branch.

| run | verdict mode (honest + mutants) | blind (`blind_corpus.py`, honest) |
|---|---|---|
| 4242 (min gas price 10⁸, committed) | 111/111 agree: 87 honest accepts, 6 accepted and 18 rejected mutants | 87/87 match (`balance_burnt` nonzero in all 87) |
| 31337 | 118/118 agree: 94 honest accepts, 5 accepted and 19 rejected mutants | 94/94 match |

The mutants are 24 per run, family-balanced, of selected honest chunks (`c`, `code`, `hdr`, `hdr2`, `t`,
`w`). Their verdicts are the cold nearcore validator's. In blind mode every produced value in the
inputs is zeroed, and the computed state root, outcome root, outgoing receipts root, gas used,
balance burnt, congestion, bandwidth requests and proposals are compared with nearcore's header. The
comparisons-on control on the blinded inputs never accepted.

Lean fix found by these fixtures (commit `fix(lean): BLS12-381 Miller-loop addition step subtracted
t10 twice`). `Pairing.additionStep` computed `2·t9 − t10 − t10`, but the transcribed crate
(`bls12_381-0.7.1/src/pairings.rs:764`) computes `t9 + t9 − t10`. The pairing was therefore not
bilinear, so any non-trivial product equal to one returned 2 instead of 0. The existing blst vectors
only had identity inputs or products ≠ 1, so they could not detect it. Breakage control: the pre-fix
checker (`replay/control-prefix-*.jsonl`) rejects exactly 2 honest chunks per run with
`InvalidOutcomesProof`. Those chunks contain `e(5a,b)e(-a,5b)` and its register-input twin. The fixed
checker accepts both. No other disagreement was found, and no spec or domain question arose.

## Files

- `cases/`: the seed-4242 selection, with 87 honest chunks and 24 mutants. Each one has `claim.bin`,
  `witness.bin` and `meta.json`.
- `cases.txt`, `honest.txt`, `mutants.txt`: case lists relative to this directory.
- `steps.json`: the scenario as `curve-steps` prints it.
- `manifest-*.json`: the collector output for each run.
- `generation.json`: binary, source and contract hashes, plus the commands.
- `replay/verdict-*.jsonl`, `replay/blind-*/`, `replay/control-prefix-*.jsonl`: the Lean results.

## Reproduction

Build `oracle/v3-successor` against the pinned checkout (`bash oracle/scripts/link-nearcore.sh`). Use
`CARGO_TARGET_DIR=/tmp/lean-global-oracle-target cargo build --release --manifest-path
oracle/v3-successor/Cargo.toml`. Then run:

```
ORACLE=/tmp/lean-global-oracle-target/release/near-arena-oracle-v3-successor
$ORACLE curve-steps > steps.json
NEAR_SUCCESSOR_SCENARIO=curve-hosts $ORACLE gen --domain d3 --seed 4242 --chains 1 --blocks 100 \
  --mutate-every 8 --code-mutant-p 0.2 --ood-cap 5000 --min-gas-price 100000000 --out RUN4242
NEAR_SUCCESSOR_SCENARIO=curve-hosts $ORACLE gen --domain d3 --seed 31337 --first-chain 1 --chains 1 \
  --blocks 100 --mutate-every 8 --code-mutant-p 0.2 --ood-cap 5000 --out RUN31337
python3 tools/d3/collect_curve_hosts.py --source RUN4242 --steps steps.json --binary $ORACLE --out OUT
(cd spec/lean/v3 && lake build nearspec-v3-check-successor)
python3 tools/mainnet-replay/blind_corpus.py --binary spec/lean/v3/.lake/build/bin/nearspec-v3-check-successor \
  --cases OUT/honest.txt --root OUT --out BLIND
spec/lean/v3/.lake/build/bin/nearspec-v3-check-successor --tier allFeatures OUT/cases/*
```

Hashes of the oracle binary, the Lean checker, the pre-fix control checker, the generator sources and
the contract are in `generation.json`. The collector fails unless every step executed exactly once.
It locates a step by method, args hash and attached gas.

## Not covered

- Register input for the BLS writers other than `p1_sum`. They share `blsWriter` and its
  `value_len / ITEM_SIZE` charge, so they are expected to behave the same, but that is not verified.
- Out-of-bounds input for `p2_sum`, the multiexps, the maps and the decompressions.
- Mid-execution host failures inside larger contracts.
- Curve hosts called from callbacks or promise chains.
- `ecrecover` cases beyond those listed. Its whole-chunk evidence is incidental to this item; key
  verification is W06.
- PV86 behaviour only. The post-NEP-488 `version = 1` path (155.yaml) is not exercised.
