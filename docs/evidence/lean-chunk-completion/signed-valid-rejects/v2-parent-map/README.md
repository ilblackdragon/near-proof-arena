# V2 layouts with a parent map: bandwidth-request parent chaining (2026-10-27)

**This was a soundness bug in every tier, the signed one included.** Before this fix Lean accepted
21 (`signed`) / 24 (`allFeatures`) chunks that nearcore rejects. It also rejected 21 / 24 valid ones.

## The rule in pinned nearcore (`44f7ae6c`, PV86)

`generate_bandwidth_request` (`runtime/runtime/src/congestion_control.rs:526-566`) chains the
outgoing buffer to `shard_layout.get_parent_shard_id(to_shard)` ahead of the shard's own buffer
whenever that call succeeds (`:545-554`). For a V2 layout,
`ShardLayout::try_get_parent_shard_id` (`core/primitives/src/shard_layout/mod.rs:253-272`) returns
`ShardLayoutV2::try_get_parent_shard_id` (`shard_layout/v2.rs:285-301`). That is the
`shards_parent_map` entry when the layout carries the map, and `None` (so `NoParent`, no chaining)
when it does not. The map is built by `validate_and_derive_shard_parent_map` from the split map,
and every unsplit shard is its own parent (`v2.rs:199-230`). So on such a layout every unsplit
shard requests its own buffer **twice**, and the child of a split requests the old parent's buffer
followed by its own.

Before this fix Lean dropped the parent map when it decoded a V2 layout (`Layout.lean`), and both
engines used the own-buffer rule on every V2 layout.

## Reachability at PV86

The case is reachable, so the rule is modelled rather than declined.

* Mainnet's static layouts from PV75 to PV81 are V2 with a parent map
  (`core/primitives/res/epoch_configs/mainnet/75.json`, `76.json`, `78.json`, `80.json`, `81.json`).
  At PV81, for example, shards 10 and 11 map to parent 0 and every other shard maps to itself.
* From PV85 (`85.json`) the mainnet config is dynamic (`dynamic_resharding_config`, no static
  layout). An epoch without a dynamic split reuses the previous layout unchanged
  (`chain/epoch-manager/src/lib.rs:693-707`, `next_next_shard_layout`). A dynamic split derives a V3
  layout (`derive_v3`, `:739`). So a PV86 epoch that has had no dynamic split since PV81 runs on the
  PV81 V2 layout with its parent map.
* An outgoing buffer under that layout is non-empty whenever the bandwidth scheduler defers a
  receipt. Because a shard is its own parent, the parent-keyed buffer *is* the own buffer. It needs
  no leftover pre-split state.
* Mainnet itself is past that window. The shard-13 W13 capture (height 221,489,407, PV86) carries
  a V3 layout (`[10, 11, 1, 8, 9, 6, 7, 4, 12, 13]`, from `tools/d3/claim_layout.py`). The pinned
  validator still decides V2 parent-map layouts at PV86, and the claim's layout is a trusted fact
  that the checker does not constrain to V3.

## The fix (both engines)

* `Layout.lean`: the V2 decoder keeps `shards_parent_map` as `Layout.v2ParentMap`.
* `D2/Queues.lean` (legacy engine, `checkD3`): `bandwidthRequests` sends a V2 layout with a map to
  `bandwidthRequestsV2P`, which chains the map's parent buffer. A shard missing from the map is
  `out of domain (c.layout): V2 shards_parent_map has no entry for shard N` (`v2ParentMissing`).
  nearcore never builds such a map.
* `Logged/D2Queues.lean` (recorder engine, `allFeatures`, through
  `StorageExecution.bandwidthRequestsR`): `bandwidthRequestsV2PL` does the same. It sits behind
  `bandwidthRequestsV2AnyL`, which both the recorder and the logged legacy mirror call.
* `Logged/D2QueuesSpec.lean`: `R_bandwidthRequestsV2P` proves the two engines' parent-map rules
  agree. `R_bandwidthRequests` covers the full three-way dispatch.

Forwarding is unchanged. V2 `get_split_parent_shard_ids` (`mod.rs:402-424`) lists only real split
parents, which are outside the layout. Both engines already exclude a non-empty buffer outside the
layout (`c.same_layout`), so no silent accept is possible there.

## Fixtures (generated by pinned nearcore, judged by the cold validator)

New scenario `yield-congestion-v2parent` (`oracle/v3-successor`, `d3gen::Scenario`). It is
`yield-congestion` (floods that make the scheduler buffer receipts) on a genesis layout rebuilt as
V2 with an identity split map, so every shard is its own parent, as on mainnet's unsplit shards
(`d3gen::genesis_layout`). Without the scenario the generator output is byte-identical to the
previous sources: seed 7, 2 chains, 40 blocks, `--mutate-every 10`, 8,545 files, `diff -r` empty.

Run `seed 102` (`summary.json` holds the command and hashes) produced 1,126 honest chunks (all
accepted by the cold validator) and 1,175 family mutants (`collect_xfam.py`: 339 headers with
buffered gas). Mutant `hdr.bandwidth_requests.own_only(derived)` (`tools/d3/bw_own_only_mutants.py`)
replaces a moved honest chunk's header requests, in the claim and in the witness, by what the
pre-fix rule computes (the own buffer only). Its nearcore verdict is derived, not run:
`validate_bandwidth_requests` (`chain/chain/src/validate.rs:280-299`) rejects any header whose
requests differ from the chunk extra nearcore computes, and the honest header is that extra.

| Population | Tier | Before (`87d7e13e`, accept / OOD / reject) | After (`c4afbc1f`) | Moves |
|---|---|---|---|---|
| 2,301 (1,126 honest + 1,175 mutants) | `signed` | 950 / 789 / 562; 21 disagree | 971 / 789 / 541; 0 disagree | 21 honest `reject (InvalidBandwidthRequests) → accept`, nearcore `ok` |
| same | `allFeatures` | 1,343 / 0 / 958; 24 disagree | 1,367 / 0 / 934; 0 disagree | 24 honest `reject → accept`, nearcore `ok` |

| same | `allFeatures` | **24 accept** | 24 reject (`InvalidBandwidthRequests`) | 24 `accept → reject` |

Every move goes toward nearcore. The before-checker accepting the own-only mutants is the
soundness bug. The 3 signed OOD are the signed tier's usual exclusions (`w.shape`, `e.wasm-α`,
`e.g_alpha`). The committed `cases/` holds 8 honest chunks and their 8 own-only mutants (listed in
`cases.txt`). `make d3-smoke` replays them at `signed` and `allFeatures`. All per-case moves are in
`run-moves-{signed,allFeatures}.jsonl`.

## Existing populations: no moves

None of the existing populations carries a V2 parent map. `tools/d3/claim_layout.py --summary`
finds 235,716 / 3,138 V2 layouts without a map in the corpus and the census, and 553 V2 without a
map plus 24 V3 among the 577 fixtures. Replayed before (`87d7e13e`) and after (`c4afbc1f`) at both
tiers, nothing moves:

|---|---|---|---|
| 3,138-case census | 735 / 2,403 / 0 | 3,138 / 0 / 0 | 0 / 0 |
| 577 fixtures | 116 / 320 / 141 | 402 / 0 / 175 | 0 / 0 |
| 235,716-case corpus | 73,577 / 2,758 / 159,381 | 76,207 / 95 / 159,414 | 0 / 0 (verdict and reason) |

(`HEAVY_MEM=40G heavy lake build NearSpecV3.Examples.RealCaseD3`): it builds, in 377 s on a loaded
host with a 20.7 GB peak.
