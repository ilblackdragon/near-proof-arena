# Exact storage-proof limit fixtures (W09)

Validator-produced chunks from the pinned nearcore `44f7ae6cd7ef08bab604e20a473bf77e35d4c993` (PV86),
generated by `oracle/v3-successor` with `NEAR_SUCCESSOR_SCENARIO=storage-limits`. Both limits are
4,000,000 B at PV86: `per_receipt_storage_proof_size_limit` (VM `RecordedStorageCounter`, upper bound
counted from the receipt's start) and `main_storage_proof_size_soft_limit`
(`check_proof_size_limit_exceed`, before each local/delayed/incoming receipt and each yield timeout).
This is independent nearcore boundary evidence for the `storageResolution` tier. Its earlier tests were
local and directed only.

The 4 MB witnesses compress to about 10 KB each, so the cases are committed as `cases.tar.gz`. Its
index and sha256s are in `cases-index.json`. Extract with `tar -xzf cases.tar.gz`, which creates `cases/`.

## Reproduce

```
NEAR_SUCCESSOR_SCENARIO=storage-limits $B gen --domain d3 --seed 99 --chains 1 --blocks 300 --p-missing 0 \
  --mutate-every 0 --code-mutant-p 0 --ood-cap 100000 --out s99
NEAR_SUCCESSOR_SCENARIO=storage-limits $B gen --domain d3 --seed 101 --first-chain 1 --chains 1 --blocks 300 \
  --p-missing 0 --mutate-every 0 --code-mutant-p 0 --ood-cap 100000 --out s101
python3 tools/d3/collect_successor_scenarios.py --source s99 --out manifest-s99.json        # also s101
python3 tools/d3/select_successor_fixtures.py --manifest manifest-s99.json --manifest manifest-s101.json \
  --out cases --mutants-per-case 3
```

`$B` is built as in `../yield-fixtures/README.md`. Lean commands are the same, with `--tier storageResolution`
and `--tier allFeatures`. The chain is quiet: no baseline transactions or injections. s99: 4 shards,
1,200 honest chunks, 199 mutants. s101: 5 shards, 1,500 honest, 199 mutants. All honest chunks were
accepted by the cold validator.

## Method

The probe receipt reads a fixed genesis value `big` and a value `pad`, whose length `t` was written in an
earlier chunk. Only that length changes between probes, never the trie structure, so the recorded size
is `const + t`. nearcore's own outcomes drive a binary search over `t`. Each lane observes both bracket
ends, converges to a one-byte flip, then repeats the flip as fresh below/at/above probes. A flip between
`t` (pass) and `t+1` (fail) means nearcore's measured quantity is exactly the limit at `t`.

## Results (s99 numbers; s101 has the same flips and recorded totals, except the soft boundary pad and absolute receipt-lane chunk sizes)

**Per-receipt limit** (`s0zlim`, receipt `W m; R big(3,950,000); R pad(t)`): passes at t = 49,330 and
fails at 49,331 (`RecordedStorageExceeded`, marker write rolled back). The fixed overhead is therefore
670 B, the same on both chains. Probes:

| probe | t | nearcore | chunk recorded bytes |
|---|---|---|---|
| final-below / at / above | 49,329 / 49,330 / 49,331 | ok / ok / **fail** | 4,001,602 / 4,001,701 / 4,001,702 |
| dup-read-at (`R big; R pad` twice) / above | 49,330 / 49,331 | ok / fail: repeated reads add nothing |  |
| panic-at | 49,330 | panic failure; reads stay recorded and the incoming receipt is delayed |  |
| removal + reinsertion (`… D k; W k`) below / at / above | 47,179 / 47,180 / 47,181 | ok / ok / **fail** | 3,999,700 / 3,999,701 / 3,999,702 |

The removal flip is 2,150 B earlier: 2,000 B is the `record_key_removal` charge, the rest is `k`'s
100-byte value and leaf. Reinsertion records nothing. The final probes carry an incoming receipt; it
is always delayed, because the chunk total exceeds the soft limit after the receipt.

**Chunk soft limit** (`s1zsoft`, local receipt `R big(3,900,000); R pad(t)` followed by an incoming
receipt in the same chunk): the incoming receipt executes at t = 97,492 and is delayed at 97,493.
s101's boundary is 97,276. The witnesses fix the absolute value. At "above", the delayed chunk's
recorded state is exactly **4,000,001 B**. At "at", it is 4,000,016 B: 4,000,000 after the local
receipt, plus the incoming receipt's 16-byte value. Both chains agree.

| probe | t | incoming receipt | note |
|---|---|---|---|
| final-below / at / above | 97,491 / 97,492 / 97,493 | same chunk / same chunk / **delayed** | 4,000,015 / 4,000,016 / 4,000,001 B recorded |
| panic-at / panic-above | 97,492 / 97,493 | same chunk / same chunk | a failed call records less: no `PromiseYieldIndices` read (`function_call.rs:154-156`) |
| multi-at | 97,492 | second local runs, both incoming delayed | the check is before each receipt |
| multi-above | 97,493 | second local and both incoming delayed (queue +3) | |
| timeout-below / above (t ∓ 256) | 97,236 / 97,748 | — | a yield timeout due in the probe chunk is resolved there (callback +1), or deferred one chunk (callback +2) |

The yield anchors that make the timeout probes possible add yield state to this shard. The soft
boundary differs from the earlier anchor-free run (98,043) for that reason, so the timeout probes
use a 256-byte margin.

**Misc** (shards of `s2zmisc`, `s3zcode`): a 3.99 MB read under a small contract and under a 1.5 MB
contract (deployed by a separate receipt, or deployed and called in one receipt) succeeds both ways.
Code does not count toward the proof (`record_code_len` is never called at the pin). Also covered:
deletion then reinsertion, deletion of a missing key (still charged), 29 removals, 29 reinsertions
then a panic (rollback), and repeated/shared reads. A 1 MB value is deleted and reinserted, then read
in the next chunk.

## Lean results

Checker `a603a893…` from `257ad1c52`. **No disagreement; no Lean change was needed.** The
`storageResolution` recorder, per-receipt check, soft-limit deferral and yield-timeout soft check
reproduce every probe:

* Full runs (`replay/full-run-verdicts.json`): 3,098 cases per tier (2,788 accepts, 310 rejects), all
  agree with nearcore on `allFeatures` and on `storageResolution`. The 548 `w.size`/`e.g_alpha`-labelled
  probe chunks are decided, not excluded.
* Committed cases (64 honest + 24 mutants): 88/88 agree on both tiers. Blind 64/64 match.
* Blind replay of all 2,700 honest chunks: 2,691 match, 0 mismatches. 9 first-chunk claims cannot be
  blinded (harness `blind_error`).
* Resources (`lean-resources.json`, `storageResolution`, sequential on a loaded host): maximum 15.6 s
  and 631 MiB, for a 7.0 MB witness (1.5 MB code + 3.99 MB read). The 4 MB boundary chunks take
  4–8 s and 300–420 MiB.

## Not covered

* Real resharding composition, global-code policy and implicit (missing-chunk) transitions at the
  limit (W11/W08); these runs have no missing chunks.
* The `Σ|values| + 2000·R` upper-bound proof (UQ-015) and the recorder/accounting link proofs. These
  fixtures validate behaviour, not the theorems.
* A chunk-soft-limit flip at exactly one byte combined with a yield timeout: the anchors move the
  boundary, so a ±256 B margin is used instead.
