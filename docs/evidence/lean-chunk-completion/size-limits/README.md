# W02 size limits: the two unmodelled/approximated witness-size limits closed (2026-10-27)

This lane closes the two size limits that W02 left excluded or approximated on
`nearspec-v3-check-successor --tier allFeatures` (workplan open item 3): the 48 MiB
compressed-witness cap (was the `w.compressed_size` exclusion) and the 64 MiB contract-code-response
cap (was unmodelled). Nothing on `allFeatures` is now excluded or approximated for a witness-size or
code-size reason. Target: nearcore 2.13.4 (`44f7ae6c`), PV86, pinned mainnet parameters.

## Decisions implemented (from the integrator, 2026-10-27)

1. **48 MiB cap → compressed input.** `allFeatures` takes the witness as distributed: a versioned
   `witness.bin` (`near-arena-cwitness-v3`) carries the `EncodedChunkStateWitness` zstd bytes. The
   relation rejects `encoded_length > MAX_COMPRESSED_STATE_WITNESS_SIZE` = 50,331,648 B
   (`partial_witness.rs:18`, checked in `validate.rs:82-88`), zstd-decodes under the 64 MiB
   `CountingRead` cut-off (`CompressedData::decode`), and validates the decoded witness as before.
   The `w.compressed_size` exclusion is removed.
2. **64 MiB code cap → out of domain `w.code_response_size`.** Fired when the borsh size of the
   cold-fetched contract code, `4 + Σ (4 + |code|)` over the chunk's accessed pre-state codes not in
   the witness, exceeds `MAX_UNCOMPRESSED_CONTRACT_CODE_RESPONSE_SIZE` = 67,108,864 B
   (`contract_distribution.rs:371-399`). See §5 for which codes count and the source.
3. **`maxWitnessChunk` premise fix** for `allFeatures` (§6); the signed file is unchanged.

## 1. A zstd decompressor in Lean (`NearSpecV3/Successor/Zstd*.lean`)

A reference RFC-8878 decompressor ported from the zstd the pinned nearcore links
(`zstd-sys-2.0.10+zstd.1.5.6`, used through `zstd::stream::Decoder`). It implements the frame header
(descriptor, window, FCS, dict-id), skippable frames, the stream decoder's loop over every
concatenated frame, Raw/RLE/Compressed blocks with `Block_Maximum_Size = min(windowSize, 128 KiB)`,
the literals section (Raw/RLE/Compressed/Treeless Huffman in 1 and 4 streams, all three size
formats), the sequences section (Predefined/RLE/FSE_Compressed/Repeat for LL, OF and ML) with
sequence execution and the three repeat offsets, `FSE_readNCount`, FSE table build/decode,
`FSE_decompress`, canonical Huffman weights (direct and FSE-compressed) and single-symbol (X1)
decoding, a logical reverse bitstream (equal to `BIT_readBits` values, with an exact end-of-stream
condition), the window-size back-reference bound, and the XXH64 content checksum (verified when the
descriptor flag is set, as the stream decoder does by default — nearcore's own frames carry no
checksum: level 1, 4 workers). The 64 MiB zip-bomb cut-off is applied by the caller
(`decompressBytesCapped`) exactly as nearcore's `CountingRead` does, at the same byte.

Allowed axioms only (`propext`, `Classical.choice`, `Quot.sound`); no `sorry`, no `native_decide`.

## 2. Differential validation against the vendored zstd 1.5.6

The reference harness `zref/` links the exact vendored zstd (`zstd-sys = "=2.0.10"`,
`zstd = "=0.13.1"`, `zstdmt`) and mirrors `CompressedData::encode`/`decode`. Scripts:
`difftest_full.py`, `difftest_real.py`, `boundaries2.py`.

| Battery | cases | result |
|---|---|---|
| Random roundtrip, 4 seeds (11/22/33/44) × 5 payload kinds × 9 sizes × levels 1/3/9/19 | 720 | 720 pass, 0 fail (`size-limits-difftest-summary.json`) |
| **Real corpus witnesses** (1,200 distinct `state_witness` from d1run/d2corpus.v2/d3c7–d3c10) × encodings {L1/w4 (nearcore's), L3/w0, L9/w4} | 3,600 | 3,600 pass, 0 fail (`size-limits-real-difftest.json`) |
| Synthetic/edge frames (multi-frame, trailing junk, truncation, single-byte corruption, bad magic, skippable, RLE/raw, good + corrupted checksum) | 20 | 19 agree with zref; 1 is Lean *stricter* than zstd on a corrupt frame (safe direction, see below) |
| **Deliberate-breakage control** (random single-bit flips in the compressed body) | 60 | every frame zref rejects (13) is also rejected by Lean; **0 soundness misses** |

The one synthetic non-match is a corrupted frame that zstd still decodes (to different bytes) while
the Lean decoder rejects it; this is `Lean reject ⊂ nearcore reject`, i.e. the decoder is more
conservative, never the reverse. No honest frame is affected (all 720 + 3,600 honest cases pass,
including every level-1/4-worker encoding, which is exactly nearcore's).

`codeResponseBytes` and both cap constants.

## 5. The `w.code_response_size` exclusion — which codes count

The codes are the chunk's **accessed pre-state contract codes that are not already in the witness**,
which a cold validator fetches in one `ContractCodeResponse`. `record_contract_call`
(`runtime/runtime/src/function_call.rs:355-392`) records a contract call only when the contract is
present in the pre-state trie with the called hash (`get_optimized_ref`, no side effects); the
validator requests the recorded hashes missing from its compiled cache (`partial_witness_actor.rs`),
and for a cold validator that is all of them. The response is a single
`CompressedContractCode` = zstd of borsh `Vec<CodeBytes>`, decoded under
`MAX_UNCOMPRESSED_CONTRACT_CODE_RESPONSE_SIZE` = 64 MiB on the borsh vector
(`contract_distribution.rs:371-399`); it is not split. These fetched codes are exactly the `codes`
appended to `witness.bin` (the oracle's cold judge appends the response contents, as
`partial_witness_tracker.rs:693-696` merges them into the base state). So the modelled condition is
`codeResponseBytes codes = 4 + Σ (4 + |code|) > 67,108,864`. The related `MAX_CONTRACTS_PER_REQUEST`
= 1282 count limit never binds (each distinct contract needs its own ≥ ~0.89 Pgas-fraction receipt;
at most ⌈1 Pgas / (780 + 108 Ggas)⌉ = 1,127 receipts per chunk).

## 6. `maxWitnessChunk` / `DomainTier` premise (task 3)

`WfClaim.DomainTier` (signed `ChallengeChunkV3.lean`) bounds every tier's completeness witness at
`maxWitnessChunk` = 64 MiB, justified by "code blobs total ≤ 4 000 000 bytes". That premise is false
at PV86: accessed pre-state code is outside the storage proof and is bounded only by the 64 MiB
code-response cap, so a `witness.bin` on `allFeatures` can hold a ≤ 48 MiB compressed witness **and**
≤ 64 MiB of code. `Config.lean` adds `allFeaturesWitnessBound` (framing + 48 MiB + 64 MiB) and
`allFeaturesWitnessBound_exceeds_maxWitnessChunk`, the corrected bound a completeness statement for
`allFeatures` must use. The signed file is left unchanged; the **signed tier's exposure** is that its
in-the-clear witness (≤ 8 MiB) plus ≤ 64 MiB of code already exceeds `maxWitnessChunk`, so even the
signed `DomainTier` bound can formally exclude a real large-code chunk — a restriction of the signed
completeness statement, not a soundness issue (`RelChunkV3`/`Rel_t` are unaffected). Whether to widen
the signed bound is a signed-statement/domain decision for the integrator.

## 7. Decoder performance (native checker, off the kernel path)

Measured with the `nearspec-v3-zstd-decode` exe (`ByteArray` output); the `allFeatures` checker holds
bytes as `List UInt8`, so its per-witness cost is higher, consistent with the existing W16 budget
note.

| input | decoded | wall | max RSS |
|---|---|---|---|
| real 0.87 MB `state_witness` (zstd-1,4w, ratio 1.99) | 887,288 B | 128 s | 14 MB |
| incompressible, raw blocks | 40 MiB | 39 s | 505 MB |
| highly compressible text (2.9 KB frame) | 30 MiB | 0.3 s | 99 MB |

The symbol-decode loop dominates for entropy-coded witnesses (≈ 145 s/MB on the 0.87 MB real
witness); raw and long-match data are fast. This is a W16 evaluation-time budget item; it is off the
`decide +kernel` path (the compressed format is exercised only by the executable checker and the
differential tests). Projected 48 MiB decode time for a fully entropy-coded witness is hours — a
reachability question, not a correctness one.
