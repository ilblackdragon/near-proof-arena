# Real shard-split fixtures, part 2 (W11): consecutive splits, threshold gates, compositions

This set extends [the first split fixtures](../resharding-fixtures/README.md) (whose numbers are
unchanged). All witnesses are validator-generated by the pinned nearcore
`44f7ae6cd7ef08bab604e20a473bf77e35d4c993` (2.13.4, PV86) through the `reshard` generator
(`oracle/v3-successor/src/reshard.rs`) and judged by the cold validator, as in the first set. No
signed source (`oracle/v3-d3/src/**`, `challenges/**`) was changed; `make pin-check` is all ok.

It closes these W11 items:

1. **Consecutive splits**, including a child that splits again, and a boundary walk across two
   layout changes.
2. **Threshold-driven split gates** (`memory_usage_threshold`, `min_child_memory_usage`), with
   exact-edge and near-threshold no-split cases.
3. **PV85 epochs and V2 layout changes in a PV86 witness**: a source-backed impossibility argument,
   with checked Lean theorems (`Successor/LayoutReach.lean`) and comments where the exclusions live.
4. **Epoch-start validator updates inside the boundary walk; genesis segments with a layout change;
   global-contract distribution routed to an obsolete layout (UQ-006).**
5. **Compositions**: a split at the per-receipt and chunk storage-proof limits (W09), and
   distribution receipts buffered/delayed across a split.

## Generator options added

All are reshard-only command-line options (no `NEAR_SUCCESSOR_SCENARIO` change); with none of them
the generator's output is unchanged.

| option | effect |
|---|---|
| `--second-split SID` | adds `SID` (a child of the first split) to `force_split_shards`; `max_number_of_shards` becomes `n+2`, and each shard keeps its chunk producers between epochs (`chunk_producer_assignment_changes_limit = 0`), so a re-split child's producers hold its state (TestEnv has no state sync) |
| `--no-force --mem-threshold T --min-child C` | no forced split: nearcore's thresholds decide. Every split-gate case records nearcore's own `total_mem_usage` and `find_trie_split` on the main transition's pre-state trie (`meta.json` `gate_probe`). A gate that did not split gets the header mutant `h.proposed_split_unmet_threshold`: exactly the split `find_trie_split` returns, which only the thresholds rule out |
| `--starve SID:E` | from the first post-split epoch, shard `SID`'s chunks are not produced for `E` epochs |
| `--zlim` | the split shard holds `s{k}zlim` (the storage-limit contract with a 3,950,000-byte value `big` and a 100,000-byte `pad2`); the parent's chunk of the resharding block runs a receipt reading both (above `per_receipt_storage_proof_size_limit`) and then one the chunk soft limit postpones |
| `--p-global-hot P` | global-contract deployments (`DeployGlobalContract`, code hash mode) in the hot window, whose distribution receipts cross the split through congested shards |

The second split needs every client to track every shard (`RESHARD_TRACK_ALL=1`); the generator then
lets those clients fetch chunk parts by request and honours forced missing chunks also when a block
finishes late. Each run writes `reshard-outcomes-<chain>.json` (nearcore's outcome tree of every
`zlim` and global-deployment transaction).

### 1. Consecutive splits

In `c31b`, `c31c`, `c37`, `c41` the parent (shard 3) splits into 4 and 5 at the epoch starting at
10061, and a child splits again at the epoch starting at 10085 (`c37`: child 5 into 6, 7 with
boundary `s0ctr2-0`; the others child 4 into 6, 7 with boundary `s0ct-0`). The second split's parent
layout is V3 and its split map keeps the first split's entry, so this exercises `splitEventV3`
(`last_split` only), `parentV3`/`childrenV3` on a V3 parent, the right child's buffered totals read in
a V3 parent layout, and the outgoing-receipt reassignment from a V3 parent. `c37` drops the parent's
chunk at both resharding blocks (`old(parent), split`), `c41` drops the children's first chunks
(`split, old(child)`, with an epoch-start validator update in the old-chunk transition).

**Two layout changes in one walk.** `c31c` starves the non-split shard 1 for both post-split epochs:
its chunk at 10085 (`seed31-02-h10085-s1`) has its main transition at 10060 (layout L0, V2) and 24
old-chunk transitions at 10061–10084 (layout L1), and is endorsed in L2. Its claim has three distinct
layouts and two epoch-start validator updates (nonzero stake changes and rewards), and it carries a
split-gate fact. Accepted, blind match.

A split *child* that is starved the same way is not a valid witness: with the child's chunks missing
through both epochs, the main transition is the original parent's chunk, which the second layout no
longer lists as a split parent, and nearcore's validator rejects the witness with
`InvalidSplitShardsIds` (`chain/chain/src/stateless_validation/chunk_validation.rs:633-644`, via
`ShardLayoutV3::get_children_shards_ids`, `core/primitives/src/shard_layout/v3.rs:330-341`). Lean
reproduces that rejection (`ReshardCore`, outgoing-receipt reassignment) with the same reason.

### 3. PV85 epochs and V2 layout changes (UQ-009)

Recorded in `spec/lean/v3/NearSpecV3/Successor/ReshardCore.lean` (module documentation) and
`Successor/LayoutReach.lean`:

* **No PV85 epoch exists on mainnet.** The pinned mainnet upgrade schedule has one entry, PV86 from
  2026-07-20 (`core/primitives/src/version.rs:58-66`); before that date a 2.13.4 node votes for the
  next epoch's version, after it for 86 (`core/primitives/src/upgrade_schedule.rs:127-158`); the
  voted version is adopted directly once it holds the stake threshold
  (`chain/epoch-manager/src/lib.rs:567-579`); 2.12.0 had `STABLE_PROTOCOL_VERSION = 84`. Mainnet
  archival RPC confirms it: block 207,762,733 is in a PV84 epoch, block 207,762,734 in a PV86 epoch,
  both with the static 9-shard V2 layout. A 2.13.4 node keeps voting 86, so every later mainnet epoch
  is PV86. A PV86 witness reaches a PV84 epoch only at the start of the first PV86 epoch: finalized
  history, whose main transitions ran under PV84 rules. PV85→PV86 segments exist only on other
  networks (testnet schedules PV86 for 2026-12-31) and in local chains such as this generator's,
  whose genesis is PV85. The `c.pv86` exclusion therefore meets no witness of the pinned mainnet
  target.
* **No V2 layout change between PV86 epochs** (`LayoutReach.no_v2_change_of_dynamic`): with
  `config(86)` dynamic — the store's entry for 86 is `epoch_configs/mainnet/85.json`, which has no
  `shard_layout` — a layout change is a `derive_v3` result. V2 *layouts* are decided: every split
  here, and mainnet's first dynamic split, has a V2 parent layout.
* **No genesis segment with a layout change** (`LayoutReach.genesis_segment_one_layout`): a segment
  reaching the genesis block contains every epoch from genesis to the witness epoch, all PV86, so the
  genesis protocol version is 86, `config(86)` must be static (`genesis.rs:64-69`), and every one of
  those epochs has the genesis layout. The genesis path's `c.same_layout` never excludes an honest
  claim.

Both theorems are proved on a transcription of `next_next_shard_layout`
(`chain/epoch-manager/src/lib.rs:679-745`) and use no axioms.

### 4. Validator updates, distribution routing (UQ-006)

* **Epoch-start validator updates inside the walk**: `seed31-02-h10085-s1` (two), `seed37-00-h10062-s4`
  and `seed41-00-h10086-s6` (one each, after the split transition).
* **Distribution routed to an obsolete layout.** A `GlobalContractDistribution` receipt keeps its
  `target_shard`; after a split the parent is no longer in the layout and nearcore resolves the target
  to its first descendant (`Receipt::receiver_shard_id`, `core/primitives/src/receipt.rs:438-462`,
  `ShardLayout::resolve_to_current_shard`, `shard_layout/mod.rs:228-237`, `v3.rs:315-326`), for
  incoming receipts (`filter_incoming_receipts_for_shard`), the delayed queue
  (`receipt_filter_fn`, `runtime/runtime/src/congestion_control.rs:868-878`) and buffer forwarding.
  `apply_distribution_current_shard` does not read the target (`global_contracts.rs:222-266`). In
  `g67` three witnesses of the left child (`01-h10062-s5`, `01-h10068-s4`, `01-h10074-s4`) carry such a
  distribution; the base checker excluded them, this branch accepts them with a blind match. Distribution
  receipts do occur in chunk witnesses: at least 43 raw honest cases carry one (the `resharding` tier stops at the first one).

### 5. Compositions

* **Storage limits at the split** (`seed61-00-h10061-s5`, witness gzipped, 4.07 MB): the main
  transition is the parent's chunk of the resharding block (10060). nearcore's outcomes
  (`reshard-outcomes-00.json`): the `zlim` receipt reading `big` and `pad2` fails at 10060 with
  `Size of the recorded trie storage proof has exceeded the allowed limit`; the next receipt is
  postponed by the chunk soft limit, inherited by both children through the delayed queue and executed
  by the child holding `s0zlim` at 10061. Both children's first chunks are accepted with a blind match.
* **Distribution receipts buffered or delayed across the split**: the `g61`/`g67` hot windows deploy
  8 and 9 global contracts while every shard bursts into a congested sink; all their witnesses are
  accepted, including the three obsolete-target cases above.

## Lean changes

All in `spec/lean/v3`:

1. `Successor/Routing.lean` (new): `Layout.resolveCurrent` (`resolve_to_current_shard`) and
   `Rcpt.routedShard` (`receiver_shard_id`), used by the successor drivers' receipt filter and
   outgoing-receipts root, the global queue policy and the pipeline's delayed-receipt peek. The signed
   `Rcpt.targetShard` is unchanged; `routedShard_of_mem` proves the two agree on every receipt whose
   target is in the layout.
2. `StorageExecution.globalTarget`: an unresolvable target is nearcore's `ShardingError` (reject);
   under a V2 layout, whose static split map is not decoded, it stays out of domain.
3. `GlobalExecution.applyDistributionL`: the obsolete-target exclusion is removed (nearcore does not
   read the target there).
4. `StorageExecution.forwardFromBufferV3L`: a buffer to an ancestor older than the last split is not
   forwarded (`get_split_parent_shard_ids` lists the last split only) instead of being excluded, and
   nearcore's empty-buffers check is modelled.
5. `Successor/LayoutReach.lean` (new) and the `ReshardCore` documentation: item 3 above.

## Not covered

* A split child whose walk crosses two layout changes has no valid witness (see §1); only nearcore's
  rejection of the producer's witness is reproduced.
* PV85→PV86 and PV84→PV86 upgrade segments: outside the pinned mainnet target (§3).
* A distribution receipt whose target left the layout through a *static* (V2) layout change stays out
  of domain (§4, `globalTarget`).
