## The change

The fix is in `spec/lean/v3/NearSpecV3/Successor/CodeResolution.lean`, `resolveCompleteCode`, and
touches **only** the race arm. The case is a call whose code is not in the witness, whose pre-state
does not require witness code, and that only a committed deploy from an earlier receipt of the same
chunk serves.

* **Before:** the complete-code policy accepted that code even when `Pipeline.deterministic` could
  not rule out that the call's preparation was pipelined before the deploy (`timely = false`).
* **After:** it reports the race exclusion that the cold policy (`globalActions`, `allFeatures`)
  already reports: `out of domain (e.wasm-α): contract preparation pipelined before the in-chunk
  deploy that serves its code`.

A deploy in the call's own receipt (`current`) still never races. Nothing else in the policy moved:
`w.code_complete` rejects of incomplete witnesses and the warm-cache rejects belong to the W08 lane.

Lean pieces:

* `CodeResolutionTests.lean` adds `#guard` cases for the arm.
* `TierRefine.complete_untimely_ood` proves that on the race arm both policies return the same
  exclusion.
* `TierRefine.raceOOD_isExclusion` proves that string is an exclusion.

## Fixture family

The family is generated by `oracle/v3-successor`, opt-in `NEAR_SUCCESSOR_SCENARIO=pipeline-race`
(`src/d3gen.rs`, `race_round`). The pinned nearcore cold validator judges every case. Exact
commands, seeds and binary hashes are in `generation.json`.

The scenario has three steps:

1. `s1raceowner` deploys a global contract by hash.
2. `s1raceglobal` uses it.
3. In 16 rounds, at one height on shard 1: two calls of `s1raceglobal`, then a fresh account
   `s1raceyNN` (no contract at genesis) deploys a round-specific module in one transaction and
   calls it in a second.

A call on a global-contract account is a shape `Successor.Pipeline` does not schedule. It marks the
chunk's preparation timing `uncertain`. The later call is then served only by the committed deploy
with `timely = false`, which is the arm. No corpus case reached it (`tier-proofs/ccg.json` has no
row where completeCodeGlobal accepts and globalActions excludes).

### Assertions (`tools/assert_race.py` → `race-assert.json`): pass

* **A1, soundness:** no tier and no binary accepts a case that nearcore rejects. This holds for
  completeCodeGlobal, globalActions and allFeatures, with both the fixed and the control binary.
* **A2, race arm:**
  * every completeCodeGlobal race exclusion carries the same reason as globalActions;
  * every case where the control's completeCodeGlobal accepted while globalActions reported the
    race is excluded by the fixed binary.
  * 0 violations.
* **A3, deliberate breakage:** the control binary reverts the arm (`if true || timely || …`). It
  violates A2 on 142 cases, so the family detects the revert.

## Honest reading

* **The pre-fix accepts were not observed to be wrong.** On all 148 race-arm cases nearcore
  accepts, and on the 40 where nearcore rejects, the pre-fix binary also rejected. In this family
  the race comes from Lean's own `uncertain` flag (a global-contract call it does not schedule), not
  from a real nearcore thread race: nearcore blocks the deploying account from pipelining, so its
  outcome here is deterministic.
* **The fix is the workplan rule applied, not a repair of an observed mismatch.** Where Lean's
  model says "possibly racing", the verdict is out of domain, never an accept.
* **Cost:** completeCodeGlobal stops deciding 186 fixture cases, the same ones globalActions already
  excludes. The 4 `reject/ok` cases that became out of domain were valid chunks that
  completeCodeGlobal rejected.
