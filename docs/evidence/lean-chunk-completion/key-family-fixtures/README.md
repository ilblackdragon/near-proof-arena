# Key-family and gas-key whole-chunk fixtures (W06, W07 gas-key part)

These chunks were produced by validators running the pinned nearcore `44f7ae6cd7ef08bab604e20a473bf77e35d4c993` at PV86.
They were generated by the separate `oracle/v3-successor` crate, using its opt-in `keys` scenario
(`oracle/v3-successor/src/keys.rs`). No signed oracle source changed. `src/chaind3.rs` is a
versioned copy of the signed `oracle/v3-d3/src/chaind3.rs`, with only the scenario hook added. With
the scenario off, a 25-block seed-77 run is byte-identical to the unmodified binary (1,147 files).

## Generation

```
bash oracle/scripts/link-nearcore.sh
cargo build --release --manifest-path oracle/v3-successor/Cargo.toml        # rustc 1.93.0
NEAR_SUCCESSOR_SCENARIO=keys near-arena-oracle-v3-successor gen --domain d3 --seed 6151 --chains 1 \
  --blocks 280 --mutate-every 10 --code-mutant-p 0.2 --ood-cap 2000 --min-gas-price 100000000 --out k6151
NEAR_SUCCESSOR_SCENARIO=keys near-arena-oracle-v3-successor gen --domain d3 --seed 1618 --chains 1 \
  --blocks 280 --mutate-every 10 --code-mutant-p 0.2 --ood-cap 2000 --out k1618
python3 tools/d3/collect_keys.py --source k6151 --binary ORACLE --out col-k6151     # likewise k1618
python3 tools/d3/select_keys_fixtures.py --manifest col-k6151/manifest.json --out cases
```

Both runs contain all 60 steps. `generation.json` records the oracle and Lean executable hashes,
the source hashes, the commands and the per-run verdict splits. `manifest-<seed>.json` gives each
step's transaction hashes and the transaction-stage result in the chunk that applied it. It also
gives nearcore's stored outcome tree (receipts included, from the generator's
`keys-outcomes-00.json`) and the sha256 of every selected case. Selected cases are:

- chunks that carry a step's transaction, either new or applied;
- the chunk that validates the application of one of its receipts, which is the next chunk of the
  executing shard after the block that stored the outcome;
- the mutants of all of those.

`cases/` holds 79 small honest chunks from seed 6151: per step, the chunk that applies the
transaction and the chunk that validates its first receipt. `cases/index.json` records each one's
origin, step labels and file hashes. The raw runs are local and are bound by hash only.

### Lean fix: high-s secp256k1 signatures

nearcore verifies a SECP256K1 signature with libsecp256k1's `secp256k1_ecdsa_verify` on
`RecoverableSignature::to_standard()`. That function rejects any `s` in the upper half of the
group order. Lean's `Secp256k1.verify` implemented textbook ECDSA, so it accepted the high-s twin
`(r, n − s)` of a valid signature. On whole chunks this showed up in two places:

- step 03, a transaction: nearcore drops it; Lean applied it and rejected the chunk on the
  post-state root;
- step 17, a delegate: nearcore fails the delegate; Lean treated it as valid and reached an access
  key that is not in the witness (`MissingTrieValue (access key)`).

Both seeds were affected. The fix adds `s < nHalfOne` to `verify`
(`spec/lean/v3/NearSpecV3/Secp256k1.lean`), plus `verify_rejects_high_s` next to the existing
known-good vector. Afterwards all four chunks accept with matching outputs.

Signed tier (`--tier signed`):

- The 3,138-case gap census (`nearcore == ok ∧ expected_rel_d3 == false` over `d3c7`–`d3c10`) is
  byte-identical before and after: 2,403 out-of-domain / 735 accept.
- `D2.actDelegate` is shared, so the two high-s delegate chunks here (`k6151 00-h10075-s1`,
  `k1618 00-h10077-s1`) move from **reject to accept at `signed`** as well.
- nearcore accepts both chunks, so both moves are corrections.
- No other signed verdict on these fixtures changes. That is 2,925 cases: 2 moves, 0 other changes.

### Remaining out-of-domain (domain questions, not fixed here)

1. **Mismatched signature and key types** in a transaction (step 06: secp key, ED25519 signature).
   `pTxD2Global` refuses the pair as `w.shape` by design (`Successor/GlobalCodecs.lean`). nearcore
   returns `InvalidSignature` and drops the transaction, and `TxD2.sigOk` already returns `false`
   for such a pair. Admitting it would be a successor-decoder domain change.
2. **ML-DSA-signed transaction** (step 25). Its two chunks are `e.mldsa_tx`, as intended: FIPS-204
   verification and the `ml_dsa_65_verification_cost` term are not modelled. The oracle metadata
   does not assert `e.mldsa_tx`, so the harness lists these chunks as "unasserted" exclusions.
3. **Receipts of that transaction**. The next two chunks of shard 0 execute the receipt and its
   refund, both carrying the ML-DSA signer key. They are `w.shape: ML-DSA-65 public key`
   (`oodMlDsaKey`, `D2/Types.lean`). This follows from (2), but receipts are a key-storage position
   the W06 widening does not cover.

### Not covered

- Byte-level malformed keys and signatures inside a chunk (bad key tag, wrong length). Chunk
  transactions are typed, so such bytes cannot be injected through the producer. The off-curve
  secp key, recovery id 4 and the malformed host key are the reachable malformed-key cases.
- ML-DSA signatures and delegates with an ML-DSA key (excluded family).
- Gas-key function-call permission on a transaction, and `add_gas_key_with_function_call`
  *success* (the host call always set an allowance, which nearcore refuses).
- Stake with a secp key.
- Not every receipt of every step has a committed chunk. Full coverage is in the manifests, which
  are bound by hash to the local runs.
