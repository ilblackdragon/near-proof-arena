## 0. Verdict

**Checkpoint 1 is sound to build on for checkpoint 2 (Lean semantics of the instruction subset), with
corrections. It is not yet sound to build on for the AIR design (checkpoint 5) or for the outcome mapping
of checkpoint 3.**

* The boundary map is careful and mostly accurate. 46 of 52 sampled citations check out exactly; the six
  problems are listed in §1. The PV86 facts that shape D3 (Wasmtime/Winch, the feature set, NaN
  canonicalisation after exactly 24 ops, finite-wasm per-range metering, the 262,144 stack budget mapped to
  `MemoryAccessViolation`, 1024/2048 pages, zero-gas preparation failures, the loading fee after a
  successful load, 89 importable host functions, the failure bit in `PartialExecutionStatus`) are right.
* The PoC's evidence is real: the harness drives nearcore's production entry points
  (`near_vm_runner::prepare` + `run`) with the PV86 config. I rebuilt both sides from this commit and
  reran a new seed: **2,000 cases, seed 7, 0 disagreements**. The instruction-level ablation is caught
  again (54 disagreements, all variant-only, and 0 after quotienting).
* **One central strategy claim is false.** `metering_equiv` (strategy §2(2), C8, RESULTS "Reading 2")
  says block-level and per-instruction metering differ only in the error variant. Once a contract has
  created any promise, nearcore's out-of-gas `burnt_gas` includes the **whole** charge of the failing
  finite-wasm range. I reproduced this on pinned nearcore (F1). `burnt_gas` is in the outcome root, so a
  per-instruction gas AIR would be unsound. The fallback the strategy already names, committing the W2
  point table to the AIR, is required, not optional.
* The boundary doc places two runtime paths outside the semantics ("node failure") that nearcore actually
  turns into failed function-call outcomes with zero gas (F2). One of them is reachable through a
  corrupted local compiled-contract cache.
* The PoC's coverage is much narrower than "every outcome class" suggests. All prepare rejections are a
  single cause, there are no function parameters or results, no data receivers, and modules are at most
  ~530 bytes (F4).

Severity counts: critical 0, high 2, medium 6, low 7, nit 5.

## 2. PoC soundness (task item 2)

### 2.1 Does the harness call the production path?

Yes, at the `near-vm-runner` API boundary. `oracle/wasm-d3/src/main.rs` calls `near_vm_runner::prepare(&ext,
wasm_config, None, gas_counter, "main")` and then `near_vm_runner::run(...)`. These are the same two
functions production uses (`RT:pipelining.rs:450`, `RT:function_call.rs:284`). The config is
`RuntimeConfigStore::new(None).get_config(86)`, and the harness asserts `vm_kind == Wasmtime`. It does not
take a shortcut: it never calls `prepare_contract` directly in run mode, and Wasmtime compiles the prepared
module with Winch on this x86_64 host. Differences from production, none of them disqualifying:

* `cache = None` → `NoContractRuntimeCache`. The cache-hit path is never exercised. On a hit, `wasm_bytes`
  for the loading fee comes from the cached record, and a cached `CompileModuleError` is replayed.
* `MockedExternal` instead of `RuntimeExt`. This is harmless for `value_return`/`panic`, but it means
  nothing about storage, promises or the recorded-storage counter has been tested.
* `output_data_receivers: vec![]`. The data-receipt fee loop in `value_return` (`W:logic.rs:4193-4211`),
  which runs for every callback-producing call in production, is untested.
* The harness compares `VMOutcome`, not the runtime's `ActionResult`. The runtime-level soft-fail mapping
  (F2) therefore sits outside what the difftest can see.

### 2.2 Is the Lean side independent of nearcore?

* **Execution (`Exec.lean`): independent.** It is a small-step interpreter over flat operator arrays,
  written against the WASM spec. It shares nothing with Wasmtime/Winch. Its NEAR-specific parts (gas
  hooks, `burn`/`process_gas_limit`, `value_return` charging order) are re-statements of nearcore
  behaviour, which is the right thing for a faithfulness spec.
* **Metering (`Prepare.lean` `gInstr`, `mergeSame`, `mergeAcross`, `optimizeWith`, `optimize`): a
  transliteration of finite-wasm 0.6.1.** Compare `finite-wasm-0.6.1/src/gas/optimize.rs`:
  `merge_same_point`/`merge_across_instructions`/`optimize_with`/`optimize` correspond case for case. The
  max-stack analysis carries finite-wasm's `stack_polymorphic` inheritance quirk (`fwPoly`). The README
  says so ("ported operator by operator"), so this is disclosed. For *faithfulness* it is acceptable,
  because nearcore's metering is defined by this algorithm. But (a) the difftest then measures port
  accuracy, not an independent account of what the gas *means*; (b) a later proof of any metering property
  is a proof about a ported imperative optimiser; and (c) B5's phrase "the PoC specifies the
  instrumentation's *meaning*" overstates what was done. See F5 and C9.

### 2.3 Is the comparison complete?

The comparison covers status, `burnt_gas`, `used_gas`, return bytes (hex) and the exact `FunctionCallError`
Debug string. That is complete for the subset's observables, with these caveats:

* in every subset case `used == burnt` (no promises), so the `used` column adds no information;
* `logs`, `compute_usage`, `balance`, `storage_usage` and `profile` are not compared. `compute_usage` is
  consensus-relevant through chunk scheduling (boundary §5). It is derived from burnt gas for pure WASM,
  so the omission is harmless today but must be added at checkpoint 3.

### 2.4 Is the generator's coverage meaningful?

It is meaningful **for the gas machinery**. The `window` family really lands out-of-gas inside a
finite-wasm range near `max_gas_burnt`, the `recursion` family hits the stack budget, and the random
family produces every i32 trap and the host errors. The ablation shows the oracle can tell metering
granularities apart. It is **thin** everywhere else:

* **Prepare rejections are a single cause.** On seed 7, 118/2000 cases are
  `PrepareError(Deserialization)`, and I verified that **all 118** are exactly the modules with no memory
  section (`r.choice([1]*12 + [17, 3000, 0])` → 0). RESULTS' "185/3000" is the same class. No malformed
  bytes, type errors, bad LEB128, limit violations, import or export rule violations, `TooMany*` errors, or
  `Instantiate`/`Memory` errors were tested. The boundary doc's §2.3 table has one **[tested]** row, and the
  other five rows (method missing → nop, `LinkError` with fee, instantiate trap, empty method, loading-fee
  failure variant) are untested. The loading-fee row is in fact exercised by the 10% "gas near loading fee"
  sub-family, but it is not labelled [tested].
* **Shape.** Every module has the same two imports, one `main`, and 0–2 helpers of type `()→()`.
  There are no function parameters or results, so argument passing, frame sizes from params and multi-frame
  value returns are untested. Max module size is 528 bytes on seed 7 (mean 210), so limits are never
  approached.
* **Blind spots** (none in the subset): `call_indirect`, tables, `elem` segments, globals (including the
  instrumentation's own), i64 arithmetic (only `i64.const`/`i64.extend_i32_u`), f32/f64, sign-extension,
  saturating truncation, bulk memory (whose **linear** fees are a separate instrumentation path,
  `instrument_v3.rs:829-872`), reference types, data segments and their instantiation traps, the start
  function, `i32.load16*`/`load8_s`/`store16`, non-natural alignment immediates, `loop`/function results,
  87 of 89 host functions, promises, the data-receiver path of `value_return`, and the `LinkError` path.
  `br_table` appears only as a void-label terminator. `memory.grow` is covered well.

The README states the subset honestly, so this is not misreporting. But the strategy's §5 sentence "Every
outcome class in the subset occurs" should not be read as "every preparation outcome". Neither the boundary
doc nor C3 should treat the §2.3 table as tested beyond its one row.

## 3. Strategy (task item 3)

**Justified:**

* **Rejecting compile-to-RISC-V.** Contract §2.3.1 makes it inadmissible without a proved compiler, and none
  exists. The "wasmi inside a zkVM" variant needs the same proof. The conclusion follows.
* **A universal machine AIR over a flat prepared IR.** The AIR is fixed per challenge, so a per-contract
  circuit is ruled out. Putting the structured→flat translation inside the Lean spec, so that no translator
  sits in the TCB, is a good call.
* **Segmentation plus recursion as the structural gap.** The arithmetic holds: 10^15 / 822,756 ≈ 1.2·10^9
  operators per chunk, against tables of at most 2^22 rows (DESIGN §8, R7). The gap is real and blocking.
* **The effort estimate (150–300k LOC, multiple person-years)** is the right order of magnitude. The internal
  sums are consistent: the 6–9 month re-execution reference matches the W1–W4 lines run partly in parallel.

**Not justified, or wrong:**

* `metering_equiv` (§2(2)): false in general (F1). Per-instruction gas in the AIR is unsound for any call
  that runs out of gas after creating a promise.

**Missing risks** (each should go into the hazard register or the strategy's risk list):

1. **Winch/Cranelift divergence is wider than H1/H3.** It is not only "accepts the module" and "NaN sign".
   There are also trap classification, native stack use (H4) and float `min`/`max`/`nearest` corner cases.
   Three wasmparser versions (0.228 / 0.236 / 0.248) sit in the pipeline, so H1 should read "everything
   that wasmparser 0.228 + finite-wasm accept, wasmparser 0.248 + Winch also accept". Nobody has measured
   whether any mainnet validators run aarch64 (the Cranelift path). Add an aarch64 leg to the difftest, or
   state the x86_64-only assumption as a protocol fact with a source.
2. **Resource errors that become outcomes.** Any `pre.instantiate` error that is neither a trap nor an
   `ErrorContainer` falls through `into_vm_error`'s last arm and becomes `LinkError{msg}` *with* the loading
   fee charged (`W:mod.rs:414-419, 1019-1026`). Pooling-allocator exhaustion and mmap failure are examples.
   H2 (the semaphore) is one instance of this class. Broaden H2.
3. **Runtime soft-fail paths** (F2): `LoadingError` and `WasmUnknownError` become 0-gas failed outcomes. Local
   cache corruption is therefore a consensus-divergence source for that node.
4. **Native stack under host calls at maximum WASM depth.** H4 only covers WASM frames. A host function
   (pairings, BLS, `ecrecover`) called at a depth near the 262,144 budget runs on the same thread stack.
   The PoC's recursion family never measures native stack use.
5. **Variable-cost host functions.** TTN charges depend on trie shape and on the chunk-level accounting
   cache (`touching_trie_node` vs `read_cached_trie_node`). Recorded-storage-size coupling is H8. This makes
   W4 gas a function of state *and* of execution history within the chunk, which `RuntimeD3` has to thread
   through.
6. **alt_bn128/BLS12-381.** The strategy prices the chips (20–60k LOC each) but not the *spec* risk. The
   specs include map-to-curve, the PV86 `not_in_group` bug behaviour (H7) and per-item cost formulas with
   item-size validation. Wycheproof does not cover NEAR's encodings.
7. **Contract size vs table height.** A 4 MiB contract (`max_contract_size` 4,194,304) needs at least one
   PREP row per byte, which already exceeds 2^22 = 4,194,304 rows. So "contract preparation as its own AIR,
   per distinct contract per proof" does not fit one proof at the limit either. Segmentation is needed for
   PREP too, or an `InD3` code-size cap.
8. **Promise DAG semantics:** data receipts, yield timeouts (lifted in D3), the refund receiver, and
   `promise_results` order. These are named in W4 but not risk-assessed. They interact with F1, because
   promise gas changes the out-of-gas `burnt_gas`.
9. **Compute usage** (`profile.compute_wasm_instruction_cost(burnt_gas)`) depends on `burnt_gas`, so the F1
   divergence propagates into chunk-level compute limits.

## 6. Findings, severity-ranked

### High

**F1: `metering_equiv` is false once a promise exists. Per-instruction gas in the AIR would be unsound.**
*Claim* (strategy §2(2), §3, §5; C8; RESULTS "Reading 2"): block-level and instruction-level metering
produce the same `burnt_gas`/`used_gas`/… and differ only in the error variant.
*Mechanism:* `burn_gas` fails at `fast_counter.gas_limit`. After a promise is created, `deduct_gas` lowers
that limit to `min(max_gas_burnt, prepaid − promises_gas)` (`L:gas_counter.rs:118-140`). But
`process_gas_limit` clamps `burnt` only to `min(prepaid, max_gas_burnt)` (`:168-201`). The out-of-gas
`burnt_gas` is then `B + c`, where `c` is the charge of the failing instrumentation point. That is the
whole finite-wasm range under block metering, but a single operator under per-instruction metering.
*Evidence* (pinned nearcore through the reviewer-built PoC harness; the probe generator is in Appendix A,
and it reproduces identically on the author's prebuilt harness). The module calls `promise_batch_create` and
`promise_batch_action_function_call(…, gas=G)`, then runs 2,000 × (`i32.const; local.set`), one pure range
of 4,000 operators:

| G (attached) | prepaid | outcome (burnt, used) |
|---|---|---|
| 100 Tgas | 300 Tgas | ok 337,413,480,225 / 101,225,475,216,159 |
| 100 Tgas | enough for 1 op of the range | **abort 337,413,480,225** / 101,222,185,014,915 `GasExceeded` |
| 100 Tgas | enough for 3,999 ops | **abort 337,413,480,225** / 101,225,474,393,403 `GasExceeded` |
| 0 (exec fees only) | enough for 1 op | **abort 337,406,944,455** / 1,222,178,479,145 |

The aborted `burnt_gas` equals the burnt gas of the *successful* run: the full 4,000-op range
(3,291,024,000 gas) is charged even when there is gas for only one operator. A per-instruction meter would
report `burnt ≈ B_start + 2·822,756` = 334,124,101,737 (G = 100 Tgas case), which is 3.29·10^9 gas less.
`gas_burnt` (and `tokens_burnt`) enter the outcome root through `PartialExecutionOutcome`, so this is
consensus-observable. The PoC cannot see it because its subset has no promises. I also confirmed that
`Exec.lean`'s `burn` uses the right clamp (`min nb (min prepaid max)`), so the Lean model is not wrong;
the strategy's generalisation is.
*Fix:* retract `metering_equiv` as stated. The AIR must commit to the W2 point table (strategy §2(2)'s
"one extra column" alternative) and charge at finite-wasm points. Restate C8 without the "makes
per-instruction gas exact" clause. Add a `promise` family to the generator (promise creation, then
out-of-gas in a long range) at checkpoint 3. Amend RESULTS "Reading 2" to say "on this promise-free subset".

**F2: The boundary doc puts two consensus-visible outcomes "outside the semantics".**
§2.2 says a corrupted or stale on-disk cache is a node failure (`VMRunnerError::LoadingError`). §4's trap
table says `Interrupt`/`HeapMisaligned`/unknown traps are "`VMRunnerError` (node error, not an outcome)".
In fact `RT:function_call.rs:328-337` returns `VMOutcome::nop_outcome(FunctionCallError::LoadingError)` and
`nop_outcome(FunctionCallError::WasmUnknownError)`: failed outcomes with 0 gas that enter the outcome root.
The first is a **determinism hazard**: a node whose compiled-contract cache is corrupted (`Module::deserialize`
fails, `W:mod.rs:744-745`) will compute a different outcome root from its peers. `ContractCodeNotPresent`
has a third mapping (`:293-309`).
*Fix:* correct §2.2 and §4. Add these rows to the §2.3 / C3 outcome table. Add a hazard H9 "node-local
cache corruption becomes a 0-gas failure". The spec should state `Rel` under the assumption that this does
not occur, and the oracle should not run with a persistent cache shared across nearcore versions.

```python
#!/usr/bin/env python3
"""Counterexample probe for strategy §2(2) `metering_equiv` (block-level vs instruction-level
metering give the same burnt_gas). Attach gas G to a promise, then run one long pure range and
run out of gas inside it. With G > 0, GasCounter::burn_gas fails at gas_limit = P - G while
process_gas_limit clamps burnt only to min(P, max_gas_burnt), so burnt = B + (charge of the failing
point). Block-level charges the whole range at once; an instruction-level meter would charge one op.
Emits harness input lines `<prepaid> <hex>`."""
import sys

OP = 822756


def uleb(n):
    out = bytearray()
    while True:
        b = n & 0x7F
        n >>= 7
        if n:
            out.append(b | 0x80)
        else:
            out.append(b)
            return bytes(out)


def sleb(n):
    out = bytearray()
    while True:
        b = n & 0x7F
        n >>= 7
        if (n == 0 and not (b & 0x40)) or (n == -1 and (b & 0x40)):
            out.append(b)
            return bytes(out)
        out.append(b | 0x80)


def vec(items):
    return uleb(len(items)) + b"".join(items)


def section(sid, payload):
    return bytes([sid]) + uleb(len(payload)) + payload


def name(s):
    return uleb(len(s)) + s.encode()


def module(n_pure, attach_gas):
    t0 = b"\x60\x00\x00"                                  # () -> ()
    t1 = b"\x60\x02\x7e\x7e\x01\x7e"                      # (i64,i64) -> i64
    t2 = b"\x60\x07" + b"\x7e" * 7 + b"\x00"               # (i64 x7) -> ()
    types = vec([t0, t1, t2])
    imports = vec([
        name("env") + name("promise_batch_create") + b"\x00" + uleb(1),
        name("env") + name("promise_batch_action_function_call") + b"\x00" + uleb(2),
    ])
    funcs = vec([uleb(0)])
    mem = vec([b"\x00" + uleb(1)])
    exports = vec([name("main") + b"\x00" + uleb(2)])
    code = bytearray()
    # idx = promise_batch_create(10, 0)   ("alice.near" at 0)
    code += b"\x42" + sleb(10) + b"\x42" + sleb(0) + b"\x10" + uleb(0)
    # promise_batch_action_function_call(idx, 1, 16, 0, 0, 32, G)
    for v in (1, 16, 0, 0, 32, attach_gas):
        code += b"\x42" + sleb(v)
    code += b"\x10" + uleb(1)
    for i in range(n_pure):                               # one long pure range
        code += b"\x41" + sleb(i % 64) + b"\x21\x00"
    code += b"\x0b"
    body = vec([uleb(1) + b"\x7f"]) + bytes(code)
    codesec = vec([uleb(len(body)) + body])
    data = vec([
        b"\x00\x41" + sleb(0) + b"\x0b" + vec([bytes([c]) for c in b"alice.near"]),
        b"\x00\x41" + sleb(16) + b"\x0b" + vec([b"f"]),
    ])
    out = b"\x00asm\x01\x00\x00\x00"
    out += section(1, types) + section(2, imports) + section(3, funcs) + section(5, mem)
    out += section(7, exports) + section(10, codesec) + section(11, data)
    return out


if __name__ == "__main__":
    n_pure = int(sys.argv[1])
    G = int(sys.argv[2])
    for p in sys.argv[3:]:
        print(p, module(n_pure, G).hex())
```
